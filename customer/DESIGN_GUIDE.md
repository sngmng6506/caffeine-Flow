# Customer Design Guide

> **AI가 읽을 때:** `customer/src`의 레이아웃, 색상, 타이포그래피, 컴포넌트, 아이콘, 애니메이션을 추가하거나 바꿀 때
> **함께 갱신할 때:** Open Flow 방향, 디자인 토큰, 공통 컴포넌트 규칙 또는 접근성 기준을 변경할 때
> **생략 가능한 경우:** 손님 화면의 시각·상호작용 결과가 바뀌지 않는 서버·DB·Electron 작업

Caffeine Flow 손님 화면의 시각·상호작용 기준이다. 사용자 문구는 [WRITING_GUIDE.md](./WRITING_GUIDE.md)를 따른다.

이 문서는 **현재 손님 UI 구현 계약**이다. 기능·상태 전이는 유지하면서 아래 규칙을 컴포넌트 단위로 적용하고, 실제 화면을 확인하며 차이를 해소한다.

## 디자인 방향: Open Flow · Editorial Violet

Open Flow는 디스콰이엇과 Threads에서 보이는 **열린 세로 피드의 정보 구조**를 참고한 모바일 음악 커뮤니티 경험이다. 비주얼 언어는 따뜻한 아이보리 캔버스, 잉크색 본문, 선명한 바이올렛 핵심 행동을 조합한 `Editorial Violet`을 사용한다. 특정 서비스의 화면을 복제하지 않고, 콘텐츠가 연속해서 읽히고 반응이 자연스럽게 이어지는 원칙만 가져온다.

- 카페에서 QR을 스캔한 손님이 설명 없이도 곡을 신청할 수 있어야 한다.
- 신청곡 하나를 하나의 피드 게시물처럼 읽고, 좋아요와 댓글을 같은 문맥에서 바로 사용할 수 있어야 한다.
- 앨범 이미지는 주인공이지만 카드 장식이 아니라 게시물의 미디어로 다룬다.
- 흰 배경, 검정에 가까운 본문, 얇은 회색 구분선을 기본으로 하고 파란색은 핵심 행동과 선택 상태에만 사용한다.
- 큰 카드 여러 장보다 하나의 연속된 surface와 행 사이 구분선으로 피드의 흐름을 만든다.
- 카페 이름과 현재 재생 정보는 상단 맥락으로 압축하고, 신청곡 피드를 첫 화면의 중심에 둔다.
- 장식용 그라데이션, 유리 효과, 과한 그림자, 서비스 복제형 로고·내비게이션은 사용하지 않는다.

Open Flow의 핵심은 **목록을 탐색하는 화면**이 아니라 **사람들이 함께 선곡하는 피드**처럼 느껴지는 것이다. 신청, 좋아요, 댓글, 재생 상태가 한 흐름에서 이어져야 하며, 그림자 대신 구분선·정렬·타이포그래피로 위계를 만든다.

## 경험 원칙

### 곡과 반응이 함께 보인다

곡 제목, 썸네일, 신청자 맥락, 재생·대기 상태가 하나의 피드 항목으로 읽혀야 한다. 좋아요와 댓글은 별도 기능 상자보다 게시물 아래의 인라인 반응 행으로 연결한다.

### 한 화면에 하나의 주 행동

피드의 전역 1차 행동은 신청곡 추가다. 각 게시물 안에서는 좋아요와 댓글을 동등한 보조 행동으로 두고, 취소·외부 이동·펼치기는 한 단계 낮춘다.

### 피드의 리듬을 끊지 않는다

상단 정보, 현재 재생, 탭, 작성 영역, 신청곡 항목이 하나의 세로 축을 공유한다. 카드가 좌우로 들쭉날쭉하거나 배경색 블록이 반복되어 스크롤 리듬을 끊지 않게 한다.

### 실시간 변화가 차분하게 느껴진다

재생 시작, 순번 변경, 좋아요 반영은 알아볼 수 있어야 하지만 화면 전체가 튀거나 흔들리지 않는다. 짧은 색 변화와 위치 전환만 사용한다.

### 작은 화면과 짧은 방문을 기준으로 한다

손님은 QR을 통해 처음 방문하며 한 손으로 조작할 가능성이 높다. 360px 너비에서도 핵심 행동과 곡 정보가 잘리지 않아야 한다.

### 상태는 색상과 문구를 함께 쓴다

파랑, 초록, 노랑 등의 색만으로 상태를 구분하지 않는다. `확인 중`, `대기 중`, `재생 중` 같은 텍스트를 함께 제공한다.

## 구현 구조

손님 UI는 다음 구조로 관리한다.

1. `customer/src/styles/tokens.css`: 색상, 타이포, 간격, radius, shadow, motion 토큰
2. `customer/src/styles/global.css`: reset, 기본 배경·폰트, focus, reduced motion
3. `customer/src/styles/components.css`: 여러 화면에서 반복되는 primitive 클래스
4. React 컴포넌트: 토큰과 공통 클래스를 조합하고 도메인별 배치만 담당

규칙:

- 새 hex 색상, 임의 shadow, 임의 radius를 컴포넌트에 직접 추가하지 않는다.
- 플랫폼 공식 색상과 콘텐츠 이미지에서 추출된 색은 예외지만 용도를 제한한다.
- 반복되는 값은 두 번째 사용 전에 semantic token으로 승격한다.
- 기존 인라인 스타일을 옮길 때 동작 변경과 대규모 시각 변경을 한 번에 섞지 않는다.
- 화면 검증 없이 여러 컴포넌트의 스타일을 일괄 치환하지 않는다.

### 강조색 사용

- 장식용 그라데이션을 사용하지 않는다.
- 파란색은 1차 CTA, 활성 탭, 재생 상태처럼 우선순위가 높은 요소에만 쓴다.
- 모바일 피드는 따뜻한 흰색 surface를 유지하고 섹션은 여백과 1px 구분선으로 나눈다. 넓은 화면의 바깥 캔버스에는 아이보리를 사용한다.
- 색이 있는 넓은 카드 배경은 경고·오류처럼 즉시 구별해야 하는 피드백에만 사용한다.
- 썸네일이 없을 때도 텍스트 대비가 유지되어야 한다.

### 상태 색상

상태값은 [상태 상수](./src/constants/recommendationStatus.js)를 경유한다. 표시 색상을 바꿀 때 상수와 이 문서의 의미를 함께 확인한다.

| 상태 | 의미 색상 | 사용자 라벨 |
| --- | --- | --- |
| `pending` | muted lavender | 확인 중 |
| `accepted` | success | 대기 중 |
| `playing` | accent blue | 재생 중 |
| `played` | content muted | 재생 완료 |
| `skipped` | warning | 건너뜀 |
| `rejected` | destructive | 신청 불가 |

색상만 보지 않아도 상태를 이해할 수 있도록 라벨이나 보조 문구를 함께 둔다.

### 플랫폼 색상

YouTube, Spotify, SoundCloud 공식 색상은 [플랫폼 상수](./src/constants/platforms.js)를 기준으로 한다.

- 공식 색상은 로고와 작은 플랫폼 배지에만 사용한다.
- 플랫폼 색상을 큰 버튼·카드 배경·페이지 테마로 확장하지 않는다.
- 브랜드 아이콘의 형태와 색을 임의로 변형하지 않는다.

## 타이포그래피

기본 글꼴은 `Pretendard Variable`, `Pretendard`, `system-ui`, `sans-serif` 순서다. Pretendard 파일을 실제로 도입하기 전에도 system fallback으로 같은 위계를 유지한다.

| 역할 | 크기 | 두께 | 줄높이 |
| --- | ---: | ---: | ---: |
| Page title | 22~24px | 700 | 1.3 |
| Card title | 18px | 700 | 1.35 |
| Hero title | 18px | 700 | 1.4 |
| Section title | 18px | 700 | 1.4 |
| Song title | 15px | 600 | 1.4 |
| Body | 14~15px | 400 | 1.55 |
| Body strong | 14px | 600 | 1.5 |
| Caption | 12px | 400 | 1.45 |
| Micro label | 11px | 600 | 1.3 |

- 사용 두께는 400, 500, 600, 700으로 제한한다.
- 곡 제목은 최대 두 줄까지 허용할 수 있지만 같은 목록에서는 줄 수를 통일한다.
- 아티스트·채널명은 곡 제목보다 한 단계 낮은 색과 크기를 사용한다.
- 입력 글자는 모바일 브라우저 자동 확대 방지를 위해 16px 이상으로 한다.
- 순위 숫자를 제외한 본문에 800 이상의 두께를 사용하지 않는다.

## 간격과 크기

기본 간격 단계:

```text
4 / 8 / 12 / 16 / 20 / 24 / 32 / 40px
```

| 역할 | 값 |
| --- | ---: |
| 작은 아이콘·텍스트 간격 | 4px |
| 같은 그룹 내부 간격 | 8~12px |
| 피드 항목 좌우 padding | 16px |
| 피드 항목 상하 padding | 16~20px |
| 섹션 사이 간격 | 16~24px |
| 페이지 좌우 여백 | 16px, 420px 이상에서 20px |
| 기본 터치 높이 | 44px |
| 핵심 CTA 높이 | 48px |

콘텐츠를 맞추기 위해 13px, 19px처럼 새로운 간격을 임의로 만들지 않는다.

## Radius와 그림자

| 토큰 | 값 | 용도 |
| --- | ---: | --- |
| `--cf-radius-badge` | 6px | 작은 상태·플랫폼 배지 |
| `--cf-radius-control` | 12px | 버튼, 입력 |
| `--cf-radius-item` | 12px | 썸네일, 미디어, 내부 패널 |
| `--cf-radius-card` | 16px | 작성 미리보기, 독립 피드백 카드 |
| `--cf-radius-overlay` | 24px | modal, bottom sheet |
| `--cf-radius-pill` | 999px | 좋아요, 필터 chip |

그림자는 떠 있는 관계를 설명할 때만 사용한다.

```css
--cf-shadow-subtle: 0 1px 2px rgba(25, 31, 40, 0.04);
--cf-shadow-raised: 0 6px 18px rgba(25, 31, 40, 0.08);
```

- 일반 목록 행에는 그림자를 사용하지 않는다.
- modal, 고정 요소 외에는 `shadow-raised`를 사용하지 않는다.
- 테두리, 배경 차이, 여백으로 충분하면 그림자를 생략한다.
- 피드 항목 자체에는 외곽 테두리와 radius를 씌우지 않는다. 항목 사이는 `--cf-stroke` 1px 구분선을 사용한다.

## 레이아웃

- 모바일 우선이며 기본 피드 너비는 `max-width: 640px`다.
- 페이지는 중앙 정렬하되 모바일에서는 피드 surface가 화면 너비를 채우고, 각 항목 내부에 16px 이상의 좌우 여백을 둔다.
- 360px에서 가로 스크롤이 생기지 않아야 한다.
- 640px 이상에서는 피드 양옆에 중립 배경이 보이게 하고 피드에는 얇은 좌우 구분선을 허용한다.
- 탭이 한 줄에 맞지 않으면 글자를 줄이지 않고 가로 스크롤을 허용한다.
- 고정 요소는 `env(safe-area-inset-bottom)`과 키보드 노출을 고려한다.
- 중요한 CTA를 화면 모서리에 겹치는 floating button으로 만들지 않는다.

기본 정보 위계:

```text
간결한 카페 헤더와 매장 상태
→ 현재 재생 중인 고정 게시물
→ 신청곡·최근 재생·인기곡 탭
→ 인라인 신청 작성 영역
→ 선택한 탭의 연속 피드
→ 개인정보 처리방침과 보조 정보
```

## 이미지

YouTube 등에서 제공하는 음악 썸네일은 기본적으로 16:9다.

- 기본 피드 미디어는 16:9 비율을 유지하고 `object-fit: cover`를 사용한다.
- 핵심 인물이나 제목이 잘리지 않도록 임의의 정사각형 crop을 기본값으로 쓰지 않는다.
- 목록에서는 같은 크기와 radius를 유지한다.
- 이미지가 없거나 URL 로드에 실패하면 surface-subtle 배경과 음악 아이콘을 사용한다.
- 빈 이미지에 깨진 URL 아이콘이나 무의미한 회색 상자만 노출하지 않는다.
- 장식용 배경 이미지 위에는 텍스트를 직접 올리지 않는다.

## 컴포넌트

### 카페 헤더

- 카페 이름을 22~24px page title로 표시하고 헤더 높이를 과도하게 키우지 않는다.
- 매장 안내와 신청 중단 상태는 제목 아래 한두 줄의 인라인 안내로 연결한다. 긴 안내만 별도 panel로 펼친다.
- 서비스 로고·영문 브랜드 라벨을 노출하거나 큰 hero 문구로 음악 목록을 밀어내지 않는다.

### 재생 중 카드

- 화면에서 가장 강한 시각 요소다.
- 피드 최상단에 고정된 강조 게시물처럼 배치한다. compact deep-plum surface, `재생 중` 라벨, 16:9 썸네일, 곡 제목, 아티스트·채널 순서로 구성한다.
- 어두운 면은 현재 재생 카드 한 곳에만 쓰고 높이를 과도하게 키우지 않는다. 강조는 색면, 라벨, 작은 재생 indicator 중 최대 두 가지로 제한한다.
- 재생 애니메이션은 작은 equalizer 또는 점 변화 중 하나만 사용한다.
- 실시간 플레이어가 멈추거나 버퍼링 중이면 같은 위치의 라벨과 아이콘을 각각 `일시정지 중`, `불러오는 중`으로 바꾸고 재생 애니메이션은 숨긴다.
- 실시간 플레이어 상태는 추천곡의 `playing` 상태와 시각적으로만 결합하며 별도 큐 상태처럼 표시하지 않는다.
- 재생 중인 곡이 없으면 카드 전체를 숨기거나 조용한 빈 상태로 대체한다.
- 썸네일과 텍스트의 최소 대비를 유지하고 긴 제목은 두 줄 이내로 제한한다.

### 신청 작성 영역

- Threads의 작성 시작점처럼 헤더와 피드 사이에 간결한 인라인 작성 영역으로 둔다.
- 링크 입력과 핵심 CTA를 같은 시야 안에 둔다.
- 플랫폼 바로가기는 보조 도구이며 입력과 CTA보다 강조하지 않는다.
- `음악 찾기` 라벨과 플랫폼 아이콘은 가까운 한 그룹으로 배치한다.
- 플랫폼 아이콘 위에 별도의 외부 링크 표시를 겹쳐 그리지 않는다. 새 창 안내는 접근성 라벨로 제공한다.
- 입력 focus에는 brand 테두리와 focus ring을 함께 제공한다.
- 입력 오류는 음악 링크 입력과 핵심 CTA 사이에 두고, 위아래 간격을 각각 12px로 맞춘다.
- 입력 전에는 큰 빈 카드를 노출하지 않는다. 입력 focus 또는 링크 붙여넣기 뒤에 필요한 도구와 미리보기를 확장한다.
- 미리보기에서는 썸네일·곡 제목·플랫폼·두 행동을 명확히 분리하되 피드 항목과 같은 좌우 정렬선을 쓴다.
- `취소`는 왼쪽 secondary, `신청`은 오른쪽 primary다. 세로 배치에서는 primary가 아래에 온다.

### 버튼

Primary:

- brand 배경, 흰 텍스트
- 높이 44~48px, pill 또는 control radius
- 한 화면의 같은 영역에 하나만 사용

Secondary:

- surface 배경, content 텍스트, stroke 테두리
- 높이 44px 이상

Tertiary:

- 배경 없이 brand 또는 content-muted 텍스트
- 중요도가 낮은 이동·펼치기 행동에 사용

Danger:

- 신청 취소처럼 실제 손실이 있는 행동에만 destructive 사용
- 목록에 항상 강한 빨간 버튼으로 노출하지 않고 확인 단계에서 강조

공통:

- disabled 상태는 opacity만 낮추지 말고 cursor와 상호작용도 비활성화한다.
- hover, pressed, focus-visible 상태를 모두 정의한다.
- 아이콘만 있는 버튼은 44px 터치 영역과 `aria-label`을 제공한다.
- 카드·행 안에서 대상이 명확한 보조 버튼은 `취소`, `댓글`처럼 짧게 쓰고, 독립 CTA와 최종 확인 행동은 대상을 명시한다.

### 입력

- surface-subtle 배경, 기본 transparent 테두리, control radius
- 높이 48px, 글자 16px 이상
- placeholder는 content-disabled를 사용하지만 라벨을 완전히 대체하지 않는다.
- 오류 시 destructive 테두리와 오류 문구를 함께 표시한다.
- URL 입력에 장식 아이콘을 여러 개 넣지 않는다.

### 탭

- 신청곡, 최근 재생, 매장 인기곡, 전체 인기곡 간 이동에 사용한다.
- 현재 재생 영역 바로 아래에 두고, 탭 전환으로 위아래 위치가 바뀌지 않게 한다.
- 신청 입력은 신청곡 탭의 콘텐츠로 배치해 다른 탭에서는 탐색 위치만 유지한다.
- 모바일 콘텐츠 영역에서 좌우 스와이프로 인접 탭을 이동할 수 있게 한다.
- 56px 이상의 뚜렷한 가로 제스처만 처리하고 세로 스크롤, 입력, 버튼, 링크 조작은 가로 전환보다 우선한다.
- 탭은 피드 상단의 sticky text tab으로 사용할 수 있다. 고정 시 카페 헤더 전체를 함께 고정하지 않는다.
- 활성 탭은 진한 텍스트와 2px underline으로 표시한다. 탭 전체를 채운 파란 pill은 사용하지 않는다.
- underline과 pill 강조를 동시에 사용하지 않는다.
- 각 탭의 터치 높이는 44px 이상이어야 한다.
- 탭 전환으로 데이터가 바뀌면 선택 상태를 `aria-selected`로 제공한다.

### 곡 목록과 SongCard

- 각 SongCard를 하나의 피드 게시물로 취급한다.
- 기본 읽기 순서는 `신청자·시간·상태 → 곡 제목·아티스트 → 썸네일 → 반응 행 → 펼친 댓글`이다. 실제 데이터가 없는 신청자·시간은 가짜로 만들지 않는다.
- 순위 화면에서는 순위를 첫 줄 또는 썸네일 옆에 추가하되 기본 피드의 구조를 유지한다.
- 목록 전체를 작은 카드 여러 개로 쪼개지 않고 흰 surface 안에서 1px 구분선과 padding을 사용한다.
- 곡 제목은 content-strong, 아티스트·채널은 content-muted를 사용한다.
- 좋아요와 댓글은 아이콘+수치의 borderless action으로 한 줄에 둔다. 활성 좋아요는 brand 색으로 표시하되 큰 배경 pill을 기본값으로 쓰지 않는다.
- 댓글 펼치기는 chevron 방향과 `aria-expanded`를 함께 갱신한다.
- 신청 취소는 본인 곡이며 취소 가능한 상태일 때만 `취소`로 표시하고, 확인 단계에서는 신청곡 취소임을 명시한다.

### 상태 배지

- 작은 텍스트 라벨 또는 낮은 대비의 badge를 사용한다.
- 색상과 문구를 함께 제공한다.
- 플랫폼 배지와 상태 배지가 나란히 있을 때 시각적 크기를 맞추되 색 역할은 섞지 않는다.
- `재생 중`은 다른 상태보다 한 단계 강하게 표시할 수 있다.

### 알림과 피드백

- 매장 안내: accent-blue-soft 배경과 정보 아이콘
- 신청 중단: warning-soft 배경과 명확한 문구
- 성공: success-soft 배경, 짧은 완료 문구
- 오류: destructive-soft 배경, 복구 방법
- 여러 알림을 한꺼번에 쌓지 않고 가장 중요한 상태를 우선한다.
- toast는 결과가 화면에서 보이지 않을 때만 사용한다.

### 빈 상태

- 중앙 정렬된 짧은 제목과 한 줄 설명을 사용한다.
- 가능한 경우 primary 또는 secondary 행동 하나를 제공한다.
- 큰 일러스트를 필수로 두지 않는다. 아이콘을 사용하면 32px 이하의 단순한 선 아이콘으로 제한한다.
- 빈 공간을 채우기 위해 장식 카드나 가짜 데이터를 넣지 않는다.

### 댓글

- 곡 게시물 아래에 thread처럼 이어지는 영역으로 펼친다.
- 답글은 들여쓰기와 stroke로 계층을 나타내며 색상만으로 구분하지 않는다.
- 댓글 작성자, 시간, 본문, 답글 행동의 정렬을 일관되게 하고 댓글마다 별도 카드 테두리를 만들지 않는다.
- 입력과 등록 버튼은 모바일 키보드가 열려도 접근할 수 있어야 한다.
- 긴 댓글은 자연스럽게 줄바꿈하고 사용자 입력을 HTML로 직접 렌더링하지 않는다.

## 아이콘

- 일반 UI 아이콘은 리디자인 첫 구현에서 `lucide-react`로 통일한다.
- 라이브러리를 사용하기 전 `customer/package.json`에 명시적으로 추가한다.
- 16px은 텍스트 인라인, 18~20px은 버튼, 24px은 독립 상태 아이콘에 사용한다.
- `currentColor`를 상속하고 컴포넌트에서 stroke 색을 반복 하드코딩하지 않는다.
- 플랫폼 로고는 공식 형태를 유지하며 일반 아이콘 라이브러리로 대체하지 않는다.
- `▶`, `👍`, `📢` 같은 이모지를 상태·행동 아이콘으로 사용하지 않는다.
- 아이콘만으로 의미를 전달할 때는 `aria-label` 또는 숨김 텍스트를 제공한다.

## 모션

| 역할 | 시간 | easing |
| --- | ---: | --- |
| 색상·opacity 반응 | 120~160ms | ease-out |
| 카드 펼치기·탭 전환 | 180~240ms | ease-out |
| toast 진입 | 200ms | ease-out |

- 실시간 업데이트마다 목록 전체를 다시 애니메이션하지 않는다.
- 순번 이동은 위치 변화가 이해될 때만 짧게 표현한다.
- 무한 반복 애니메이션은 재생 중 indicator 하나에만 허용한다.
- `prefers-reduced-motion: reduce`에서는 이동과 반복 애니메이션을 제거한다.
- 클릭 반응을 늦추는 300ms 이상의 장식 애니메이션을 사용하지 않는다.

## 접근성

- 일반 텍스트는 WCAG AA 대비 4.5:1 이상을 목표로 한다.
- 큰 텍스트와 비텍스트 UI도 최소 3:1 대비를 유지한다.
- 모든 버튼, 링크, 입력, 탭에 `:focus-visible` 표시를 제공한다.
- 터치 대상은 가능한 44×44px 이상으로 만든다.
- 아이콘 버튼에는 동작을 설명하는 `aria-label`을 제공한다.
- 탭에는 적절한 tab 역할과 `aria-selected`, 펼침 요소에는 `aria-expanded`를 사용한다.
- 색상만으로 상태나 오류를 전달하지 않는다.
- 썸네일 alt는 정보가 주변 텍스트와 완전히 중복되면 빈 문자열을 사용한다.
- 로딩 상태는 필요한 경우 `aria-live`로 알리되 잦은 실시간 목록 변경을 모두 읽지 않는다.
- 브라우저 확대 200%와 360px 너비에서 핵심 기능을 사용할 수 있어야 한다.
- 사용자 입력을 위험한 HTML 방식으로 렌더링하지 않는다.

## 반응형 검증 기준

UI 변경 후 최소 다음 너비를 확인한다.

| 너비 | 목적 |
| ---: | --- |
| 360px | 작은 Android 화면, 긴 카페명·곡 제목 |
| 390px | 일반 모바일 기준 |
| 430px | 큰 모바일 기준 |
| 480px | 넓은 모바일·작은 창의 피드 밀도 |
| 640px | 데스크톱 피드 최대 너비 경계 |

각 너비에서 확인할 항목:

- 가로 스크롤이 생기지 않는가
- 탭과 버튼의 문구가 잘리지 않는가
- 곡 제목과 채널명이 다른 행동을 밀어내지 않는가
- 키보드가 열려도 입력과 CTA를 사용할 수 있는가
- safe area에서 고정 요소가 겹치지 않는가

## 피해야 할 패턴

- Spotify의 검정·초록, Apple Music의 카드 구조 등 특정 서비스를 그대로 모사
- Threads의 로고·프로필 구조·내비게이션 또는 디스콰이엇의 고유 컴포넌트를 그대로 복제
- 모든 신청곡을 둥근 독립 카드로 만들고 카드 사이에 큰 배경 여백을 두는 방식
- 모든 카드에 그라데이션, blur, glow를 적용하는 방식
- 밝은 배경 위의 연한 색상 텍스트처럼 대비가 낮은 조합
- 한 화면에 여러 primary 버튼 사용
- 정보 위계를 대신하는 과도한 그림자와 radius
- 12px 이하 본문, 44px보다 작은 핵심 터치 대상
- 임의 hex 색상과 임의 spacing을 컴포넌트마다 추가
- 상태를 색상이나 이모지만으로 표현
- 플랫폼 브랜드 색상을 Caffeine Flow의 주 색상처럼 사용
- 실제 화면 확인 없이 전체 인라인 스타일을 한 번에 치환

## AI UI 변경 절차

1. 변경할 실제 컴포넌트, 상태 상수, 플랫폼 상수를 먼저 읽는다.
2. 현재 동작과 사용자 흐름을 유지한 채 한 컴포넌트의 목표를 정한다.
3. 기존 token으로 해결할 수 있는지 확인하고 임의 값을 추가하지 않는다.
4. 문구가 바뀌면 [WRITING_GUIDE.md](./WRITING_GUIDE.md)를 함께 확인한다.
5. 360px, 390px, 480px, 640px에서 화면을 직접 확인한다.
6. 키보드 focus, 터치 크기, 상태 텍스트, reduced motion을 확인한다.
7. `npm run build --prefix customer`를 실행한다.
8. 새로운 반복 패턴이나 디자인 결정을 만들었다면 이 문서를 갱신한다.
