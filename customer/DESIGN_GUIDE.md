# Customer Design Guide

> **AI가 읽을 때:** `customer/src`의 레이아웃, 색상, 타이포그래피, 컴포넌트, 아이콘, 애니메이션을 추가하거나 바꿀 때
> **함께 갱신할 때:** Cyber Queue 방향, 디자인 토큰의 역할, 공통 컴포넌트 규칙, 접근성 기준을 변경할 때
> **생략 가능한 경우:** 손님 화면의 시각·상호작용 결과가 바뀌지 않는 서버·DB·Electron 작업

손님 화면의 시각·상호작용 계약이다. 사용자 문구는 [WRITING_GUIDE.md](./WRITING_GUIDE.md)를 따른다. 기능과 상태 전이는 유지한 채 아래 규칙을 컴포넌트 단위로 적용하고 실제 화면을 확인하며 차이를 해소한다.

## 디자인 방향: Cyber Queue

**블랙 캔버스, 애시드 옐로 신호 면, 핑크 오프셋 레이어**를 쓰는 단일 다크 테마다. 재생과 신청이라는 두 순간만 검은 피드 위로 떠 보이고, 곡 목록은 평평한 연속 행으로 빠르게 읽힌다.

- 핵심은 모든 것을 형광으로 칠하는 것이 아니라 **지금 나오는 음악과 다음 곡을 신청하는 행동만 신호처럼 떠오르게 하는 것**이다.
- 블랙과 차콜을 기본 면으로 쓰고 애시드 옐로는 현재 재생, 신청 작성, 활성 탭, 1차 CTA에만 쓴다.
- 두 신호 패널은 같은 두 색을 **역할만 바꿔** 쓴다. 현재 재생은 형광 면 + 핑크 오프셋, 신청 작성은 핑크 면 + 형광 오프셋이다. 오프셋 거리는 둘 다 `7px`로 같고, 구분은 면 색이 한다.
- 핑크는 이 두 자리 밖으로 넓히지 않는다. 반복 목록과 일반 행에는 쓰지 않는다.
- 큰 카드 여러 장 대신 하나의 연속된 검은 surface와 행 사이 구분선으로 피드의 흐름을 만든다.
- 앨범 이미지는 작은 16:9 미디어로 쓰고 형광 면과 경쟁할 만큼 키우지 않는다.
- 카페 이름과 현재 재생은 상단 맥락으로 압축하고 신청곡 피드를 첫 화면의 중심에 둔다.
- 장식용 그라데이션·glow·blur, 둥근 카드 남용, 특정 음악 서비스의 로고·내비게이션 복제는 쓰지 않는다.

## 경험 원칙

- **곡과 반응이 함께 보인다.** 곡 제목, 썸네일, 신청자 맥락, 상태가 하나의 피드 항목으로 읽힌다. 좋아요와 댓글은 별도 상자가 아니라 게시물 아래 인라인 반응 행이다.
- **한 화면에 하나의 주 행동.** 피드의 전역 1차 행동은 신청곡 추가다. 게시물 안에서는 좋아요와 댓글이 동등한 보조 행동이고 취소·외부 이동·펼치기는 한 단계 낮다.
- **신호 면과 목록을 분리한다.** 신호 면만 떠 보이게 하고 목록은 한 세로 축의 평평한 행으로 유지한다.
- **실시간 변화가 차분하다.** 재생 시작·순번 변경·좋아요 반영은 알아볼 수 있되 화면 전체가 튀지 않는다.
- **작은 화면과 짧은 방문 기준.** QR로 처음 들어와 한 손으로 쓰며, 360px에서도 핵심 행동과 곡 정보가 잘리지 않는다.
- **상태는 색과 문구를 함께 쓴다.** 색만으로 구분하지 않고 `확인 중`, `대기 중`, `재생 중` 같은 텍스트를 함께 둔다.

## 구현 구조

```text
customer/src/styles/tokens.css      색상·타이포·간격·radius·shadow·motion 토큰
customer/src/styles/global.css      reset, 기본 배경·폰트, focus, reduced motion
customer/src/styles/components.css  여러 화면에서 반복되는 primitive 클래스
React 컴포넌트                       토큰과 공통 클래스를 조합하고 도메인 배치만 담당
```

- 새 hex 색상, 임의 shadow, 임의 radius를 컴포넌트에 직접 추가하지 않는다.
- 플랫폼 공식 색상과 콘텐츠 이미지에서 추출한 색은 예외지만 용도를 제한한다.
- 반복되는 값은 두 번째 사용 전에 semantic token으로 승격한다.
- 인라인 스타일을 옮길 때 동작 변경과 대규모 시각 변경을 섞지 않는다.
- 화면 검증 없이 여러 컴포넌트의 스타일을 일괄 치환하지 않는다.

## 색상

실제 값은 `customer/src/styles/tokens.css`가 단일 기준이다. 이 문서는 각 토큰의 **역할**만 정의하고 hex를 복사하지 않는다.

| 토큰 계열 | 역할 |
| --- | --- |
| `--cf-brand*` | 애시드 옐로. 1차 CTA, 활성 탭, 핵심 선택과 그 hover/pressed/tint |
| `--cf-canvas`, `--cf-surface`, `--cf-surface-subtle` | 페이지 블랙 배경, 연속 피드, 입력·댓글·비활성 차콜 면 |
| `--cf-content*` | 제목·본문·보조·캡션·비활성 텍스트의 4단계 위계 |
| `--cf-stroke`, `--cf-stroke-strong` | 기본 테두리와 focus·핵심 구분선 |
| `--cf-now-playing`, `--cf-composer*` | 현재 재생의 형광 면과 신청 작성의 핑크 면 |
| `--cf-layer-pink`, `--cf-accent-lilac` | 두 핵심 패널 뒤의 오프셋 레이어 |
| `--cf-on-pink*` | 핑크 면 위에 올리는 텍스트·테두리 색 |
| `--cf-on-dark*` | 형광 면 위에 올리는 텍스트·아이콘 색 |
| `--cf-accent-blue*` | 옐로와 의미가 겹치지 않는 작은 정보성 신호 |
| `--cf-success*`, `--cf-warning*`, `--cf-destructive*` | 완료, 주의·신청 중단, 오류·취소 확인 |
| `--cf-status-*` | 상태별 전경·배경 쌍 |
| `--cf-focus` | 키보드 focus ring |

사용 규칙:

- 장식용 그라데이션을 쓰지 않는다.
- 피드와 넓은 화면의 바깥 캔버스는 모두 블랙을 유지하고 차콜 면으로 깊이만 구분한다.
- 플랫폼 바로가기는 신청 패널 위에 투명 배경과 검정 테두리를 써서 플랫폼 고유색과 경쟁하지 않게 한다.
- 썸네일이 없을 때는 차콜 면 위에 음악 아이콘과 낮은 불투명도의 애시드 옐로 선 패턴을 공통으로 쓴다.

### 상태 색상

상태값과 라벨은 [상태 상수](./src/constants/recommendationStatus.js)를 경유한다. 표시 색을 바꿀 때 상수와 이 문서의 의미를 함께 확인한다.

| 상태 | 의미 | 사용자 라벨 |
| --- | --- | --- |
| `pending` | 어두운 tint 위 애시드 옐로 | 확인 중 |
| `accepted` | success | 대기 중 |
| `playing` | 애시드 옐로 면 위 블랙 | 재생 중 |
| `played` | content muted | 재생 완료 |
| `skipped` | warning | 건너뜀 |
| `rejected` | destructive | 신청 불가 |

`재생 중`은 다른 상태보다 한 단계 강하게 표시할 수 있다. 색만으로 상태를 전달하지 않는다.

### 플랫폼 색상

공식 색상은 [플랫폼 상수](./src/constants/platforms.js)가 기준이다. 로고와 작은 배지에만 쓰고 큰 버튼·카드 배경·페이지 테마로 확장하지 않으며 아이콘의 형태와 색을 변형하지 않는다.

## 타이포그래피

기본 글꼴은 `Pretendard Variable`, `Pretendard`, `system-ui`, `sans-serif` 순서다. 실제 폰트 파일 도입 전에도 system fallback으로 같은 위계를 유지한다.

| 역할 | 크기 | 두께 | 줄높이 |
| --- | ---: | ---: | ---: |
| Page title | 22~24px | 700 | 1.3 |
| Card / Hero / Section title | 18px | 700 | 1.35~1.4 |
| Song title | 15px | 600 | 1.4 |
| Body | 14~15px | 400 | 1.55 |
| Body strong | 14px | 600 | 1.5 |
| Caption | 12px | 400 | 1.45 |
| Micro label | 11px | 600 | 1.3 |

- 기본 두께는 400·500·600·700으로 제한하고 카페명과 섹션 제목만 800까지 허용한다. 본문과 설명에는 800 이상을 쓰지 않는다.
- 곡 제목은 두 줄까지 허용하되 같은 목록에서는 줄 수를 통일한다.
- 아티스트·채널명은 곡 제목보다 한 단계 낮은 색과 크기를 쓴다.
- 입력 글자는 모바일 자동 확대 방지를 위해 16px 이상으로 한다.

## 간격·크기·radius

기본 간격 단계는 `4 / 8 / 12 / 16 / 20 / 24 / 32 / 40px`다. 13px, 19px 같은 값을 임의로 만들지 않는다.

| 역할 | 값 |
| --- | ---: |
| 작은 아이콘·텍스트 간격 | 4px |
| 같은 그룹 내부 | 8~12px |
| 피드 항목 좌우 padding | 16px |
| 피드 항목 상하 padding | 16~20px |
| 섹션 사이 | 16~24px |
| 페이지 좌우 여백 | 16px, 420px 이상에서 20px |
| 기본 터치 높이 | 44px |
| 핵심 CTA 높이 | 48px |

radius는 `--cf-radius-*` 토큰을 쓴다. 버튼·입력·미디어·패널은 사각(0)이고 배지만 2px, modal·bottom sheet는 16px, 원형 상태 점 등 제한적 legacy 요소만 pill이다.

## 그림자

그림자는 떠 있는 관계를 설명할 때만 쓴다. 현재 재생은 `--cf-shadow-signal`(핑크 `7px 7px`), 신청 작성은 `--cf-shadow-signal-invert`(형광 `7px 7px`)를 쓰고 일반 목록 행에는 그림자가 없다. 거리는 같고 색만 반대이므로, 새 오프셋 거리나 색을 컴포넌트마다 만들지 않는다.

- 오프셋 방향·거리·색을 컴포넌트마다 바꾸지 않는다.
- 테두리, 배경 차이, 여백으로 충분하면 그림자를 생략한다.
- 피드 항목에 외곽 테두리와 radius를 씌우지 않는다. 곡·순위 항목 사이는 `--cf-brand` 1px 구분선을 쓴다.

## 레이아웃

- 모바일 우선이며 기본 피드 너비는 `max-width: 640px`다. 중앙 정렬하되 모바일에서는 surface가 화면 너비를 채우고 각 항목 내부에 16px 이상 좌우 여백을 둔다.
- 360px에서 가로 스크롤이 생기지 않아야 한다.
- 640px 이상에서도 바깥과 피드의 블랙 배경을 유지하고 얇은 차콜 좌우 구분선만 허용한다.
- 네 개의 음악 탭은 화면 너비를 25%씩 균등하게 나눈다. 긴 카페명은 칸 안에서 말줄임하고 가로 스크롤을 만들지 않는다.
- 고정 요소는 `env(safe-area-inset-bottom)`과 키보드 노출을 고려한다.
- 중요한 CTA를 화면 모서리에 겹치는 floating button으로 만들지 않는다.

기본 정보 위계:

```text
카페 헤더와 매장 상태 → 현재 재생 고정 게시물 → 음악 탭
→ 인라인 신청 작성 영역 → 선택한 탭의 연속 피드 → 개인정보 처리방침과 보조 정보
```

## 이미지

음악 썸네일은 기본 16:9다.

- 목록에서는 작은 16:9 썸네일을 곡 제목·채널과 같은 행에 두고 `object-fit: cover`와 같은 크기·radius를 유지한다.
- 현재 재생과 신청 미리보기만 더 큰 16:9 미디어를 쓸 수 있다.
- 임의의 정사각형 crop을 기본값으로 쓰지 않는다.
- 이미지가 없거나 로드에 실패하면 surface-subtle 배경, 음악 아이콘, 낮은 불투명도의 애시드 옐로 선 패턴을 공통으로 쓴다. 깨진 URL 아이콘이나 빈 회색 상자를 노출하지 않는다.
- 장식용 배경 이미지 위에 텍스트를 직접 올리지 않는다.

## 컴포넌트

### 카페 헤더

- 카페 이름을 22~24px page title로 표시하고 헤더 높이를 키우지 않는다.
- 매장 안내와 신청 중단 상태는 제목 아래 한두 줄 인라인 안내로 연결하고, 긴 안내만 별도 panel로 펼친다.
- 서비스 로고·영문 브랜드 라벨이나 큰 hero 문구로 음악 목록을 밀어내지 않는다.

### 재생 중 카드

- 화면에서 가장 강한 시각 요소이며 피드 최상단의 애시드 옐로 신호 면이다. `재생 중` 라벨 → 16:9 썸네일 → 곡 제목 → 아티스트·채널 순서로 구성한다.
- 텍스트와 아이콘은 블랙이고 카드 뒤 오른쪽 아래에 7px 핑크 오프셋을 둔다. 모서리를 자르거나 둥글리지 않고 glow·blur를 넣지 않는다.
- 재생 애니메이션은 작은 equalizer 또는 점 변화 중 하나만 쓴다.
- 실시간 플레이어가 멈추거나 버퍼링 중이면 같은 위치의 라벨과 아이콘을 `일시정지 중`, `불러오는 중`으로 바꾸고 재생 애니메이션을 숨긴다. 이 상태는 추천곡 `playing`과 시각적으로만 결합하며 별도 큐 상태처럼 표시하지 않는다.
- 재생 중인 곡이 없으면 카드를 숨기거나 조용한 빈 상태로 대체한다.

### 신청 작성 영역

- 헤더와 피드 사이의 간결한 인라인 작성 영역이다. 접힌 상태·입력·미리보기 모두 핑크 면과 형광 `7px` 오프셋을 쓰고, 그 위에서는 검정 면이 1차 CTA다. 이 조합을 다른 영역에 복제하지 않는다.
- 채도 높은 면 위의 비활성 버튼에 `opacity` 감산을 쓰지 않는다. 면은 유지하고 글자만 낮춘다. 반투명은 배경색과 섞여 버튼을 탁한 덩어리로 만든다.
- 링크 입력과 핵심 CTA를 같은 시야 안에 둔다. 입력 전에는 큰 빈 카드를 노출하지 않고 focus 또는 붙여넣기 뒤에 도구와 미리보기를 확장한다.
- 입력 focus에는 brand 테두리와 focus ring을 함께 제공한다. 입력 오류는 링크 입력과 CTA 사이에 두고 위아래 간격을 각각 12px로 맞춘다.
- 플랫폼 바로가기는 보조 도구다. 입력과 CTA보다 강조하지 않고, 각 아이콘의 접근 가능한 이름으로 이동 목적과 새 창 안내를 제공하며 별도 `음악 찾기` 라벨이나 외부 링크 표시를 겹쳐 그리지 않는다.
- 미리보기는 썸네일·곡 제목·플랫폼·두 행동을 분리하되 피드 항목과 같은 좌우 정렬선을 쓴다. `취소`는 왼쪽 secondary, `신청`은 오른쪽 primary이며 세로 배치에서는 primary가 아래다.

### 버튼

| 종류 | 형태 | 용도 |
| --- | --- | --- |
| Primary | 애시드 옐로 배경, 블랙 텍스트, 높이 44~48px 사각 | 한 영역에 하나뿐인 핵심 행동 |
| Secondary | 블랙·차콜 배경, content 텍스트, stroke 테두리, 높이 44px 이상 | 보조 행동 |
| Tertiary | 배경 없이 brand 또는 content-muted 텍스트 | 중요도가 낮은 이동·펼치기 |
| Danger | destructive | 신청 취소처럼 실제 손실이 있는 행동의 확인 단계 |

- disabled는 opacity만 낮추지 말고 cursor와 상호작용도 비활성화한다.
- hover, pressed, focus-visible 상태를 모두 정의한다.
- 아이콘만 있는 버튼은 44px 터치 영역과 `aria-label`을 제공한다.
- 대상이 명확한 인라인 버튼은 `취소`, `댓글`처럼 짧게, 독립 CTA와 최종 확인은 대상을 명시한다.

### 입력

차콜 배경, 옐로 focus 테두리, 사각 control, 높이 48px, 글자 16px 이상을 쓴다. placeholder는 content-disabled를 쓰되 라벨을 완전히 대체하지 않고, 오류 시 destructive 테두리와 문구를 함께 표시한다. URL 입력에 장식 아이콘을 여러 개 넣지 않는다.

### 탭

- 신청곡, 최근 재생, 매장 인기곡, 전체 인기곡 사이 이동에 쓰며 기본 상태에서 `repeat(4, minmax(0, 1fr))`로 같은 너비를 쓴다.
- `{카페명} TOP` 탭이 활성화되면 그 탭만 이름 길이만큼 확장한다. 나머지는 최소 64px을 유지하고 전체 폭을 넘으면 탭 영역에서만 가로 스크롤을 허용한다.
- 현재 재생 영역 바로 아래에 두고 탭 전환으로 위아래 위치가 바뀌지 않게 한다. 신청 입력은 신청곡 탭의 콘텐츠로 배치한다.
- 모바일에서는 탭 콘텐츠 전체에서 좌우 스와이프로 인접 탭을 이동한다. 8px 이동부터 방향을 판정해 가로 이동량이 세로와 비슷하거나 크면 가로로 잠그고, 세로가 우세하면 목록 스크롤을 유지한다. 44px 이상 가로 이동에서 탭을 전환한다.
- 입력·선택·외부 링크는 스와이프 시작 영역에서 제외하고, 곡 행과 인라인 버튼 위에서는 탭하지 않고 가로로 움직인 경우만 허용한다.
- 활성 탭은 애시드 옐로 텍스트와 4px underline으로 표시한다. pill 강조를 함께 쓰지 않는다.
- 각 탭의 터치 높이는 44px 이상이고 선택 상태는 `aria-selected`로 제공한다. sticky로 쓸 때 카페 헤더 전체를 함께 고정하지 않는다.

### 곡 목록과 SongCard

- 각 SongCard는 하나의 피드 게시물이다. 읽기 순서는 `신청자·시간·상태 → 작은 썸네일 + 곡 제목·아티스트 → 반응 행 → 펼친 댓글`이며 없는 신청자·시간을 가짜로 만들지 않는다.
- 순위 화면은 순위·작은 썸네일·곡 정보를 같은 행에 둔다.
- 목록을 작은 카드로 쪼개지 않고 블랙 surface 안에서 1px 차콜 구분선과 padding을 쓴다. 긴 순위 목록의 짝수 행은 surface-subtle로만 구분하고 형광 면은 선택·재생 상태에 남긴다.
- 곡 제목은 content-strong, 아티스트·채널은 content-muted다.
- 좋아요와 댓글은 아이콘 + 수치의 borderless action으로 한 줄에 둔다. 활성 좋아요는 brand 색으로 표시하되 큰 배경 pill을 기본으로 쓰지 않는다. 인기곡의 좋아요 칸은 고정 폭과 `tabular-nums`로 하트의 세로 축을 맞춘다.
- 댓글 펼치기는 chevron 방향과 `aria-expanded`를 함께 갱신한다.
- 신청 취소는 본인 곡이며 취소 가능한 상태일 때만 `취소`로 표시하고 확인 단계에서 신청곡 취소임을 명시한다.
- 곡 행을 550ms 길게 누르면 재신청용 원본 링크를 복사한다. 12px 이상 움직이면 취소해 스크롤과 스와이프를 우선하고, 행 안의 좋아요·댓글·취소 버튼에서는 복사를 시작하지 않는다.

### 상태 배지·알림·빈 상태

- 상태 배지는 작은 텍스트 라벨이나 낮은 대비의 badge로 색과 문구를 함께 제공한다. 헤더의 `신청 가능`은 별도 초록 팔레트 없이 차콜 면과 애시드 옐로 테두리·점·문구로 표시한다. 플랫폼 배지와 나란히 둘 때 크기는 맞추되 색 역할은 섞지 않는다.
- 알림은 종류별 배경을 쓴다. 신청곡 안내는 차콜 배경과 옐로 왼쪽 신호선, 신청 중단은 warning-soft, 성공은 success-soft, 오류는 destructive-soft에 복구 방법을 함께 둔다.
- 여러 알림을 쌓지 않고 가장 중요한 상태를 우선한다. toast는 결과가 화면에서 보이지 않을 때만 쓰며 링크 복사처럼 본문이 바뀌지 않는 결과에 사용한다.
- 빈 상태는 중앙 정렬된 짧은 제목과 한 줄 설명, 가능하면 행동 하나를 둔다. 큰 일러스트를 필수로 두지 않고 아이콘은 32px 이하 선 아이콘으로 제한한다. 빈 공간을 채우려고 장식 카드나 가짜 데이터를 넣지 않는다.

### 댓글

- 곡 게시물 아래에 thread처럼 이어지는 영역으로 펼친다.
- 답글은 들여쓰기와 stroke로 계층을 나타내며 색상만으로 구분하지 않는다.
- 작성자·시간·본문·답글 행동의 정렬을 일관되게 하고 댓글마다 별도 카드 테두리를 만들지 않는다.
- 입력과 등록 버튼은 모바일 키보드가 열려도 접근할 수 있어야 한다.
- 긴 댓글은 자연스럽게 줄바꿈하고 사용자 입력을 HTML로 직접 렌더링하지 않는다.

## 아이콘

- 일반 UI 아이콘은 `lucide-react`로 통일하고 `currentColor`를 상속한다. 컴포넌트에서 stroke 색을 반복 하드코딩하지 않는다.
- 16px은 텍스트 인라인, 18~20px은 버튼, 24px은 독립 상태 아이콘에 쓴다.
- 플랫폼 로고는 공식 형태를 유지하며 일반 아이콘으로 대체하지 않는다.
- `▶`, `👍` 같은 이모지를 상태·행동 아이콘으로 쓰지 않는다.
- 아이콘만으로 의미를 전달할 때는 `aria-label` 또는 숨김 텍스트를 제공한다.

## 모션

모션은 장식이 아니라 입력 피드백, 상태 변화, 공간적 연결, 갑작스러운 변화 완화 중 하나의 목적을 가져야 한다. 목적을 한 문장으로 설명할 수 없으면 추가하지 않는다.

사용 빈도에 따라 강도를 정한다.

- 좋아요·댓글·탭처럼 하루에 수십 번 사용할 수 있는 행동은 색상 변화나 미세한 눌림 반응만 쓴다.
- modal·bottom sheet·toast처럼 가끔 등장하는 요소만 진입·퇴장 모션을 허용한다.
- 온보딩·최초 성공처럼 드문 순간에만 제한적인 장식 모션을 검토한다.
- 키보드로 실행하는 반복 행동과 실시간 목록 전체에는 진입 애니메이션을 쓰지 않는다.

| 역할 | 시간 | easing |
| --- | ---: | --- |
| 버튼 눌림 피드백 | 100~160ms | strong ease-out |
| 색상·opacity·hover 반응 | 120~160ms | ease |
| 작은 popover·tooltip | 125~200ms | strong ease-out |
| 카드 펼치기·등장·퇴장 | 180~240ms | strong ease-out |
| 화면 안 위치 이동·형태 변화 | 180~240ms | strong ease-in-out |
| toast 진입 | 200ms | strong ease-out |
| spinner·재생 indicator | 상태가 지속되는 동안 | linear |

- 등장·퇴장은 `ease-out`, 화면 안에서의 이동·형태 변화는 `ease-in-out`, hover·색상 변화는 `ease`, 일정한 반복은 `linear`를 쓴다. 입력 직후 느리게 출발하는 `ease-in`은 사용하지 않는다.
- 공통 곡선은 motion token으로 관리한다. 기본 후보는 strong ease-out `cubic-bezier(0.23, 1, 0.32, 1)`, strong ease-in-out `cubic-bezier(0.77, 0, 0.175, 1)`이며 비슷한 곡선을 컴포넌트마다 새로 만들지 않는다.
- 기본적으로 `transform`, `opacity`, 색상만 전환하고 `transition: all`을 사용하지 않는다. `width`, `height`, `margin`, `padding`, `top`, `left`의 연속 애니메이션은 피한다.
- 눌림 피드백은 `scale(0.97)`을 기본으로 하되 작은 아이콘 버튼·드래그 핸들처럼 크기 변화가 인지를 방해하면 배경·색상 반응만 쓴다. 등장 요소는 `scale(0)`에서 시작하지 않는다.
- 빠르게 반복하거나 되돌릴 수 있는 toggle·toast·탭 전환은 중간 상태에서 자연스럽게 방향을 바꿀 수 있는 CSS transition을 우선한다. spring은 사용자의 손가락을 따르는 제스처와 복귀처럼 물리성이 필요한 경우에만 검토한다.
- 실시간 업데이트마다 목록 전체를 다시 애니메이션하지 않는다. 순번 이동은 위치 변화가 이해될 때만 짧게 표현한다.
- 탭 전환은 스와이프 방향과 일치하는 8~12px 이내 이동과 opacity로 제한한다. 빠르게 왕복해도 이전 전환이 다음 입력을 막지 않고, 실시간 목록 갱신으로 탭 진입 모션을 다시 실행하지 않는다.
- 무한 반복 애니메이션은 재생 중 indicator 하나에만 허용하며 일시정지·버퍼링에서는 중단한다.
- `prefers-reduced-motion: reduce`에서는 위치 이동·scale·반복을 제거한다. 상태 이해에 필요한 짧은 opacity·색상 피드백과 기능 완료 안내는 유지할 수 있으며, 탭 결과는 이동 없이 즉시 보여준다.
- hover 기반 이동은 `(hover: hover) and (pointer: fine)` 환경에서만 허용한다.
- 클릭 반응을 늦추는 300ms 이상의 장식 애니메이션, 기본 blur·bounce·3D 효과, 목록 전체 stagger는 쓰지 않는다.

## 접근성

- 일반 텍스트는 WCAG AA 4.5:1 이상, 큰 텍스트와 비텍스트 UI도 최소 3:1 대비를 유지한다.
- 모든 버튼·링크·입력·탭에 `:focus-visible` 표시를 제공하고 터치 대상은 44×44px 이상으로 만든다.
- 아이콘 버튼에는 `aria-label`, 탭에는 `aria-selected`, 펼침 요소에는 `aria-expanded`를 쓴다.
- 색상만으로 상태나 오류를 전달하지 않는다.
- 썸네일 alt는 정보가 주변 텍스트와 완전히 중복되면 빈 문자열을 쓴다.
- 로딩 상태는 필요할 때만 `aria-live`로 알리고 잦은 실시간 목록 변경을 모두 읽지 않는다.
- 브라우저 확대 200%와 360px 너비에서 핵심 기능을 쓸 수 있어야 한다.
- 사용자 입력을 위험한 HTML 방식으로 렌더링하지 않는다.

## 변경 절차와 체크리스트

1. 변경할 컴포넌트, 상태 상수, 플랫폼 상수, 토큰을 먼저 읽는다.
2. 현재 동작과 사용자 흐름을 유지한 채 한 컴포넌트의 목표를 정한다.
3. 기존 토큰으로 해결할 수 있는지 확인하고 임의 값을 추가하지 않는다.
4. 문구가 바뀌면 [WRITING_GUIDE.md](./WRITING_GUIDE.md)를 함께 확인한다.
5. 360px·390px·480px·640px에서 화면을 직접 확인한다. 각 너비에서 가로 스크롤, 문구 잘림, 곡 제목이 다른 행동을 밀어내는지, 키보드가 열렸을 때 입력과 CTA 사용, safe area 겹침을 본다.
6. 새로운 반복 패턴이나 디자인 결정을 만들었다면 이 문서를 갱신한다.

- [ ] 블랙 피드와 제한적인 애시드 옐로 강조를 유지했는가
- [ ] 형광 면 + 핑크 오프셋(현재 재생)과 핑크 면 + 형광 오프셋(신청 작성)의 역할을 뒤섞지 않았는가
- [ ] 곡 정보와 반응이 하나의 피드 항목으로 읽히고 불필요한 외곽 카드로 분절되지 않았는가
- [ ] 새 색상·간격·radius·shadow를 임의로 추가하지 않았는가
- [ ] 플랫폼 공식 색상을 로고·배지 밖으로 확장하지 않았는가
- [ ] 16:9 썸네일과 이미지 fallback이 일관적인가
- [ ] 같은 역할에 같은 타이포와 컴포넌트 변형을 썼고 primary 행동이 영역마다 하나인가
- [ ] 360px에서도 가로 스크롤과 잘림이 없는가
- [ ] 터치 크기, focus, ARIA, 대비, reduced motion을 지켰는가
- [ ] 상태가 색상 외의 문구로도 전달되는가
- [ ] 실제 화면을 컴포넌트 단위로 확인했고 `npm run build --prefix customer`가 통과했는가
