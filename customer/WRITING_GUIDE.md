# Customer Writing Guide

> **AI가 읽을 때:** `customer/src`의 사용자 노출 문구, 상태 라벨, 버튼, 빈 상태, 오류·성공 메시지를 추가하거나 바꿀 때
> **함께 갱신할 때:** 손님 화면의 목소리, 핵심 용어, 상태 표현 또는 반복되는 문구 패턴을 변경할 때
> **생략 가능한 경우:** 사용자에게 보이는 문구가 바뀌지 않는 로직·스타일·빌드 설정 변경

Caffeine Flow 손님 화면의 문구 기준이다. 시각 스타일과 접근성 구현은 [DESIGN_GUIDE.md](./DESIGN_GUIDE.md)를 따른다.

## 목소리

문구는 **차분하고 친절한 카페 DJ**처럼 말한다.

- **바로 이해되게:** 현재 상태와 다음 행동을 먼저 알려준다.
- **짧고 부드럽게:** 자연스러운 해요체를 쓰고 같은 설명을 반복하지 않는다.
- **음악 경험답게:** 신청·대기·재생의 흐름이 느껴지되 과도한 감탄이나 유행어는 피한다.
- **사용자를 존중하며:** 잘못을 탓하지 않고 해결 방법을 안내한다.

음악적인 표현은 환영·빈 상태처럼 가벼운 순간에만 제한적으로 쓴다. 오류, 거절, 취소, 개인정보 문구는 분위기보다 정확성을 우선한다.

## 기본 원칙

### 상태와 다음 행동을 함께 쓴다

문제나 빈 상태만 말하지 않는다. 사용자가 지금 할 수 있는 행동까지 안내한다.

- `데이터가 없습니다.` → `아직 신청곡이 없어요. 듣고 싶은 곡을 신청해 보세요.`
- `요청 실패` → `신청하지 못했어요. 잠시 후 다시 시도해 주세요.`
- `현재 신청을 받지 않습니다` → `지금은 신청곡을 받고 있지 않아요. 잠시 후 다시 확인해 주세요.`

### 버튼에는 결과를 쓴다

`확인`, `계속`, `완료`처럼 결과가 모호한 표현을 단독으로 사용하지 않는다.

- `곡 확인` → `신청곡 확인하기`
- `신청하기` → `이 곡이 맞나요?`처럼 대상이 명확한 미리보기에서는 `신청`
- 선택을 되돌리는 행동 → 같은 미리보기에서는 `취소`
- `더 보기` → 맥락에 따라 `신청곡 더 보기`, `댓글 더 보기`

대상이 화면에서 명확하고 공간이 좁은 경우에만 `취소`, `닫기` 같은 짧은 표현을 허용한다.

### 사용자 언어를 쓴다

서버 구현이나 내부 상태 이름을 노출하지 않는다.

- `recommendation 생성 실패` → `신청곡을 추가하지 못했어요.`
- `filter_status rejected` → `이 곡은 매장 신청 기준에 맞지 않아 신청할 수 없어요.`
- `Socket 연결 오류` → `새 소식을 불러오지 못했어요. 잠시 후 다시 확인해 주세요.`
- `slug가 유효하지 않습니다` → `이 QR 코드로 연결된 카페를 찾지 못했어요.`

### 같은 개념에는 같은 단어를 쓴다

화면마다 `추천곡`, `요청곡`, `신청 음악`으로 바꾸지 않는다. 손님이 추가하는 음악은 항상 **신청곡**이다.

서버 코드의 식별자와 사용자 문구는 달라도 된다. 사용자 문구를 바꿀 때 서버 상태값 자체를 바꾸지 않는다.

### 한 문장에는 한 가지 핵심만 둔다

제목이 말한 내용을 본문에서 반복하지 않는다. 정보와 행동이 함께 필요하면 두 문장으로 나눈다.

```text
이미 대기 중인 곡이에요.
다른 곡을 선택해 주세요.
```

## 문체와 표기

- 설명, 오류, 성공 메시지: 해요체
- 화면 제목, 탭, 섹션 제목, 상태 배지: 짧은 명사형 허용
- 버튼: 행동 결과가 드러나는 동사형
- 느낌표: 특별한 성취에도 한 번만 사용하며 일반 성공 메시지에서는 생략
- 버튼·탭·배지에는 마침표를 쓰지 않음
- 문장에는 필요한 경우 마침표를 사용
- 말줄임표는 `...`보다 `…`를 사용
- 숫자와 단위는 붙여 씀: `3번째`, `7일`, `10곡`
- 영문 플랫폼명은 공식 표기 유지: `YouTube`, `Spotify`, `SoundCloud`
- 반말, 과도한 유행어, 의성어, 사용자에게 부담을 주는 표현을 사용하지 않음
- 이모지로 의미를 전달하지 않으며 일반 UI 의미는 아이콘과 텍스트로 표현

## 핵심 용어

| 개념 | 사용자 용어 | 사용 기준 |
| --- | --- | --- |
| 손님이 추가한 곡 | 신청곡 | `추천곡`, `요청곡`과 혼용하지 않음 |
| URL을 분석하는 단계 | 곡 확인 | 진행 문장은 `곡 정보를 확인하고 있어요` |
| 서버 판단 전 상태 | 확인 중 | 내부 상태 `pending`의 사용자 표현 |
| 재생이 확정된 상태 | 대기 중 | 내부 상태 `accepted`의 사용자 표현 |
| 현재 나오는 곡 | 재생 중 | 내부 상태 `playing`의 사용자 표현 |
| 재생이 끝난 곡 | 재생 완료 | 내부 상태 `played`의 사용자 표현 |
| 재생하지 않고 넘긴 곡 | 건너뜀 | 내부 상태 `skipped`의 사용자 표현 |
| 정책상 받지 않은 곡 | 신청 불가 | 내부 상태 `rejected`를 그대로 노출하지 않음 |
| 곡에 보내는 반응 | 좋아요 | `투표`, `추천`과 혼용하지 않음 |
| 카페별 집계 | 매장 인기곡 | 짧은 탭에서는 `{카페명} TOP` 허용 |
| 전체 카페 집계 | 전체 인기곡 | 짧은 탭에서는 `전체 TOP` 허용 |
| 사장님이 작성한 알림 | 매장 안내 | `공지사항`보다 손님 화면에 자연스럽게 표현 |
| 신청자를 구분하는 이름 | 내 닉네임 | 기기 기반 이름이라는 구현 설명은 노출하지 않음 |

상태값과 표시 위치는 [상태 상수](./src/constants/recommendationStatus.js)를 기준으로 한다. 새 용어가 여러 화면에 반복되면 이 표에 먼저 추가한다.

## 화면 요소별 작성법

### 카페 헤더와 안내

- 카페 이름은 장식 문구 없이 그대로 표시한다.
- 기본 안내는 `듣고 싶은 음악을 신청해 보세요.`로 간결하게 쓴다.
- 영업·신청 중단 상태는 짧게 알리고 다시 확인할 시점을 안내한다.
- 사장님 공지는 `매장 안내`라는 맥락으로 제공하되 내용 자체를 임의로 고쳐 쓰지 않는다.

```text
지금은 신청곡을 받고 있지 않아요.
잠시 후 다시 확인해 주세요.
```

### 재생 중

- 상태 라벨은 `재생 중`으로 고정한다.
- 곡 제목과 아티스트·채널명을 문구로 반복하지 않는다.
- 재생 중인 곡이 없을 때 빈 카드를 억지로 노출하지 않는다.

### 신청 폼

- 입력 placeholder는 입력값의 종류와 방법을 알려준다.
- 지원 플랫폼을 문장에 모두 반복하기보다 화면의 플랫폼 표시와 함께 사용한다.
- 미리보기 단계에서는 선택한 곡과 최종 행동을 분명히 구분한다.

권장 흐름:

```text
음악 링크를 붙여 넣어 주세요
[신청곡 확인하기]

이 곡이 맞나요?
[취소] [신청]
```

### 대기열과 상태

- `pending`과 `accepted`의 차이를 사용자에게 필요한 수준으로만 설명한다.
- 내부 검토 방식이나 AI 사용 여부를 기본 화면에서 강조하지 않는다.
- 순번은 보장되는 경우에만 단정한다. 변동될 수 있으면 `현재 3번째로 기다리고 있어요.`처럼 현재 상태임을 표시한다.

```text
신청했어요.
현재 3번째로 기다리고 있어요.
```

### 인기곡 정렬

- 인기곡 문맥이 이미 보이면 `신청 많은 순`, `좋아요 많은 순` 대신 `신청순`, `좋아요순`을 사용한다.
- 정렬 기준은 짧은 명사형으로 쓰고 문장형 설명을 반복하지 않는다.

### 빈 상태

현재 상태와 다음 행동을 함께 안내한다. 행동할 수 없는 화면에서는 상태만 차분하게 설명한다.

```text
아직 신청곡이 없어요.
듣고 싶은 곡을 신청해 보세요.
```

```text
최근 재생된 곡이 없어요.
곡이 재생되면 여기에 기록돼요.
```

```text
아직 인기곡 순위가 없어요.
신청곡이 쌓이면 순위를 볼 수 있어요.
```

### 로딩

- 무엇을 불러오는지 구체적으로 쓴다.
- 짧게 끝나는 버튼 로딩은 `확인 중…`, `신청 중…`, `등록 중…`처럼 작성한다.
- 페이지 로딩에는 `불러오는 중…`만 단독으로 쓰지 않는다.

```text
신청곡을 불러오고 있어요.
```

### 오류

오류 문구는 다음 순서를 따른다.

1. 사용자 관점에서 무슨 일이 생겼는지
2. 지금 할 수 있는 해결 방법

- HTTP 상태, 오류 코드, API 응답 원문을 그대로 노출하지 않는다.
- 입력 문제여도 사용자를 탓하지 않는다.
- 재시도로 해결되지 않는 문제에는 매장 직원 문의 등 실제 가능한 방법만 안내한다.

| 상황 | 권장 문구 |
| --- | --- |
| 링크를 읽지 못함 | `곡 정보를 확인하지 못했어요. 링크를 확인하고 다시 시도해 주세요.` |
| 이미 대기 중 | `이미 대기 중인 곡이에요. 다른 곡을 선택해 주세요.` |
| 현재 재생 중 | `지금 재생 중인 곡이에요. 다른 곡을 선택해 주세요.` |
| 허용하지 않는 플랫폼 | `이 매장에서는 {플랫폼명} 신청곡을 받고 있지 않아요.` |
| 네트워크 오류 | `연결이 원활하지 않아요. 잠시 후 다시 시도해 주세요.` |
| 카페를 찾지 못함 | `이 QR 코드로 연결된 카페를 찾지 못했어요. 매장에 문의해 주세요.` |

### 성공 메시지

- 완료된 행동을 과거형으로 알린다.
- 화면에서 결과가 즉시 보이면 중복 토스트를 만들지 않는다.
- 순번이나 좋아요 수처럼 유용한 추가 결과가 있을 때만 함께 표시한다.

- `신청곡을 추가했어요.`
- `좋아요를 표시했어요.`
- `신청을 취소했어요.`

### 확인 다이얼로그

- 제목에서 대상과 행동을 명확히 쓴다.
- 본문에서 대기열에 미치는 영향과 되돌릴 수 있는지 설명한다.
- 버튼은 `돌아가기`와 실제 위험 행동으로 구성한다.

```text
이 신청곡을 취소할까요?
대기열에서 사라지며 다시 들으려면 새로 신청해야 해요.

[돌아가기] [신청 취소하기]
```

### 댓글과 답글

- `댓글 추가...`보다 행동을 안내하는 `댓글을 남겨 보세요`를 사용한다.
- 입력 중인 사용자의 닉네임은 필요할 때만 한 번 보여준다.
- 빈 상태는 참여를 권하되 강요하지 않는다.

```text
아직 댓글이 없어요.
이 곡에 대한 이야기를 남겨 보세요.
```

### 외부 서비스 이동

- 링크만 보고 이동할 서비스를 예상할 수 있어야 한다.
- 새 창·새 탭 이동에는 플랫폼명을 포함한다.
- 외부 서비스의 계정·결제·재생 정책을 Caffeine Flow의 기능처럼 약속하지 않는다.

## 피해야 할 표현

- `정상적으로`, `성공적으로`: 완료 사실만으로 충분하면 제거
- `해당`, `관련`, `진행`: 구체적인 대상을 직접 작성
- `유효하지 않은`, `실패했습니다`: 사용자가 이해할 수 있는 문제로 바꿈
- `확인`, `계속`, `완료`: 결과가 모호한 버튼에는 사용 금지
- `추천`, `투표`: 손님 화면의 `신청`, `좋아요`와 혼용 금지
- `pending`, `accepted`, API, DB, Socket, slug, token 같은 구현 용어
- `무조건`, `곧`, `바로`: 시간이나 결과를 보장할 수 없으면 사용 금지
- 반복되는 느낌표, 장식용 이모지, 과도한 음악 은유

## AI 문구 변경 절차

1. 실제 컴포넌트와 상태 상수를 먼저 확인한다.
2. 이 문서의 핵심 용어와 기존 화면의 같은 개념을 찾는다.
3. 문구가 약속하는 결과가 실제 동작과 일치하는지 확인한다.
4. 오류에는 복구 방법, 빈 상태에는 가능한 다음 행동을 포함한다.
5. 접근 가능한 이름과 화면 문구가 같은 행동을 설명하는지 확인한다.
6. 여러 화면에 반복될 새 용어라면 구현 전에 이 문서를 갱신한다.

## 문구 변경 체크리스트

- [ ] 문구만 보고 현재 상태와 다음 행동을 이해할 수 있는가
- [ ] `신청곡`, `좋아요`, `재생 중` 등 기존 용어를 일관되게 사용했는가
- [ ] 해요체·명사형·동사형을 요소 역할에 맞게 사용했는가
- [ ] 제목과 본문이 같은 내용을 반복하지 않는가
- [ ] 오류와 빈 상태가 가능한 해결 방법을 안내하는가
- [ ] 사용자를 탓하거나 불필요하게 불안하게 하지 않는가
- [ ] 내부 상태값과 개발 용어가 노출되지 않는가
- [ ] 버튼 문구가 실제 실행 결과와 일치하는가
- [ ] 외부 서비스 이동과 위험 행동이 분명한가
- [ ] 작은 화면에서도 번역·줄바꿈을 고려한 길이인가
