# Owner Design Guide

> **AI가 읽을 때:** `owner/src`의 레이아웃, 색상, 타이포그래피, 컴포넌트와 상호작용을 추가하거나 바꿀 때
> **함께 갱신할 때:** 사장님 화면의 디자인 방향, 공통 컴포넌트, 버튼 위계 또는 반응형 기준을 변경할 때
> **생략 가능한 경우:** 화면 결과가 바뀌지 않는 서버·DB 작업과 Electron 내부 수정

Caffeine Flow 사장님 화면의 시각·상호작용 기준이다. 사용자 문구는 [WRITING_GUIDE.md](./WRITING_GUIDE.md)를 따른다.

이 문서는 목표 UI 계약이다. 기존 인라인 스타일은 컴포넌트 단위로 점진적으로 정리하며, 화면 검증 없이 전체 스타일을 한 번에 치환하지 않는다.

## 디자인 방향: Calm Operations

사장님 앱은 영업 중 빠르게 상태를 확인하고 음악을 관리하는 데스크톱 운영 도구다. 소비자 금융 앱처럼 쉽고 안정적인 위계를 사용하되, 좁은 좌측 패널에서도 필요한 정보가 한눈에 들어오도록 밀도를 유지한다.

- 명확한 제목, 단일 핵심 행동, 차분한 중립색과 이해하기 쉬운 피드백을 사용한다.
- 데스크톱 운영 도구에 맞는 정보 밀도, 행 중심 설정, 빠른 탐색 구조를 사용한다.
- 브랜드의 로고, 고유 색상, 화면 배치를 그대로 복제하지 않는다.
- 손님 화면의 Cyber Queue 컬러와 장식을 사장님 화면으로 가져오지 않는다.
- 화면은 조용하게 유지하고 재생·오류·위험 상태에만 필요한 강조를 쓴다.

핵심은 **꾸미는 것보다 판단 시간을 줄이는 것**이다.

## 경험 원칙

### 영업 중 행동을 우선한다

신청곡 확인, 수락, 재생 상태 확인처럼 자주 쓰는 기능을 먼저 보여준다. 계정 관리, QR 변경, 로그인 복구처럼 드물게 쓰는 기능은 설정이나 접이식 영역에 둔다.

### 한 영역에 하나의 주요 행동

같은 카드나 행에서 Primary 버튼을 여러 개 사용하지 않는다. 가장 중요한 행동 하나를 Primary로 두고 나머지는 Secondary 또는 Text 버튼으로 내린다.

### 상태와 행동을 분리한다

`재생 중`, `신청 받는 중`, `AI 자동수락 켜짐`은 상태다. 상태 배지를 버튼처럼 보이게 만들지 않고, 변경 행동은 별도 컨트롤로 제공한다.

### 예외 기능은 기본 화면에서 숨긴다

쿠키 초기화, 개발자 도구, 강제 복구는 일반 기능과 같은 위계로 노출하지 않는다. `문제 해결`, `개발자 기능` 같은 접이식 영역 안에 둔다.

### 좁은 좌측 패널을 기준으로 한다

사장님 UI는 Electron 왼쪽 패널에서 사용된다. 넓은 웹 페이지를 축소한 형태가 아니라, 420~720px 폭에서 자연스럽게 재배치되는 구조로 설계한다.

## 정보 구조

기본 내비게이션은 세 영역을 우선한다.

1. `신청 목록`: 기본 BGM, 재생 중, 대기 곡, 새 신청
2. `이력`: 처리된 신청곡의 최신 기록
3. `설정`: 운영, 매장 정보, 음악 서비스, 계정과 도움말

설정 내부 권장 순서:

```text
운영 설정
→ 매장 정보
→ 음악 서비스
→ 계정 및 도움말
→ 문제 해결·개발자 기능
```

- `손님 신청 플랫폼`과 `음악 서비스 바로가기`를 혼동하지 않는다.
- 전자는 손님이 신청할 수 있는 범위, 후자는 오른쪽 BGM 화면과 로그인 진입점이다.
- 관련 기능을 합칠 때도 목적이 다른 컨트롤은 제목과 설명으로 명확히 분리한다.

## 색상

### 권장 팔레트

| 역할 | 권장값 | 용도 |
| --- | ---: | --- |
| Canvas | `#F5F6F8` | 앱 기본 배경 |
| Surface | `#FFFFFF` | 콘텐츠와 설정 면 |
| Surface subtle | `#F2F4F6` | 보조 영역, 빈 상태 |
| Text strong | `#191F28` | 제목, 핵심 값 |
| Text | `#333D4B` | 기본 본문 |
| Text muted | `#6B7684` | 설명, 보조 정보 |
| Text disabled | `#AAB2BD` | 비활성 정보 |
| Stroke | `#E5E8EB` | 구분선, 입력 테두리 |
| Primary | `#3182F6` | 주요 행동, focus |
| Primary hover | `#1B64DA` | 주요 행동 hover |
| Success | `#00A878` | 정상 완료, 연결됨 |
| Warning | `#F59F00` | 확인이 필요한 상태 |
| Danger | `#E42939` | 삭제, 실패, 중단 위험 |

- 새 색상은 역할 없이 임의로 추가하지 않는다.
- 플랫폼 공식 색상은 작은 로고, 점, 배지에만 사용한다.
- YouTube 빨강, Spotify 초록, SoundCloud 주황을 버튼이나 카드 전체 배경으로 확장하지 않는다.
- 색상만으로 상태를 전달하지 않고 문구나 아이콘을 함께 사용한다.
- 장식용 그라데이션, glow, 강한 그림자를 사용하지 않는다.

## 타이포그래피

기본 글꼴은 시스템 한글 UI 폰트를 사용한다.

| 역할 | 크기 | 두께 | 줄높이 |
| --- | ---: | ---: | ---: |
| Page title | 20~22px | 700 | 1.35 |
| Section title | 15~17px | 700 | 1.4 |
| Item title | 14px | 600~700 | 1.45 |
| Body | 13~14px | 400 | 1.5 |
| Caption | 11~12px | 400~500 | 1.45 |
| Key metric | 24~28px | 700 | 1.2 |

- 한 화면에서 4단계 이상의 글자 위계를 만들지 않는다.
- 제목을 모두 굵게 만들어 위계를 잃지 않는다.
- 설명은 12px 아래로 줄이지 않는다.
- 긴 곡 제목은 최대 두 줄, 목록에서는 한 줄 말줄임을 기본으로 한다.

## 간격과 크기

기본 간격 단계:

```text
4 / 8 / 12 / 16 / 20 / 24 / 32px
```

| 역할 | 기준 |
| --- | ---: |
| 같은 행 내부 간격 | 8px |
| 같은 그룹 내부 간격 | 12~16px |
| 섹션 사이 간격 | 20~24px |
| 화면 좌우 여백 | 16~20px |
| 기본 컨트롤 높이 | 40px |
| 중요한 컨트롤 높이 | 44px |
| 아이콘 버튼 최소 크기 | 40×40px |

- 콘텐츠를 억지로 맞추기 위해 임의의 간격을 추가하지 않는다.
- 좁은 패널에서는 여백을 줄이되 컨트롤 높이와 클릭 영역은 유지한다.

## Radius와 깊이

- Button, input: 8~10px
- Card, details: 10~12px
- Modal: 14~16px
- Status pill: `999px`, 짧은 상태에만 사용

일반 카드에는 그림자를 사용하지 않는다. 흰색 surface, 얇은 stroke, 간격으로 구분한다. 떠 있는 모달이나 업데이트 알림처럼 실제 레이어 관계가 있을 때만 약한 그림자를 허용한다.

카드 안에 다시 외곽선 카드가 반복되지 않게 한다. 같은 맥락의 항목은 하나의 surface 안에서 행과 구분선으로 연결한다.

## 레이아웃

### 헤더

- 카페명과 영업 중 자주 확인하는 상태만 노출한다.
- 신청 접수와 AI 자동수락 같은 핵심 토글은 일관된 위치에 둔다.
- URL, 카페명 수정, 로그아웃처럼 자주 쓰지 않는 행동은 설정으로 이동한다.
- 공지는 한 줄로 요약하고 선택했을 때 편집한다.

### 신청 목록

권장 위계:

```text
기본 BGM 상태
→ 재생 중
→ 대기 곡
→ 새 신청
```

- 실제 재생 중인 곡 영역은 다른 목록보다 한 단계 강하게 표시한다.
- `수락`처럼 내부 처리 행동보다 `재생 중`처럼 현재 결과를 제목으로 쓴다.
- 대기 곡과 새 신청을 같은 카드 스타일로 반복하지 않고 제목, 개수, 구분선으로 나눈다.
- 빈 상태는 큰 카드 대신 짧은 안내 한두 줄로 표시한다.
- 드래그 대상과 클릭 버튼이 충돌하지 않도록 hover와 focus 상태를 구분한다.

### 이력

- 최신 기록을 기본으로 보여준다.
- 날짜, 처리 상태, 곡 정보를 한 행에서 빠르게 읽을 수 있게 한다.
- 필터와 날짜 선택은 목록보다 강하게 보이지 않게 한다.
- 되돌릴 수 있는 행동과 불가능한 행동을 명확히 구분한다.

### 설정

- 설정 대분류는 접이식 섹션을 사용할 수 있다.
- summary에는 제목과 한 줄 설명만 둔다.
- 펼친 영역은 행 또는 작은 섹션으로 구성하며 카드 중첩을 피한다.
- 저장되지 않은 변경이 있을 때만 저장 버튼을 노출할 수 있다.
- 복구·초기화·개발자 기능은 마지막에 배치하고 기본적으로 접는다.

### 음악 서비스

- YouTube, YouTube Music, Spotify, SoundCloud를 동일한 행 구조로 표시한다.
- 왼쪽에는 서비스명과 계정 조건, 오른쪽에는 행동을 둔다.
- `오른쪽 화면에서 열기`를 Primary, `로그인`을 Secondary로 사용한다.
- 로그인 초기화는 `로그인 문제 해결`에 숨긴다.
- 서비스 자체의 자동재생, 요금제, 재생 가능 여부를 앱이 보장하는 것처럼 표현하지 않는다.

## 컴포넌트

### 버튼

Primary:

- Primary 배경과 흰색 텍스트
- 저장, 수락, 오른쪽 화면에서 열기 등 현재 영역의 핵심 행동
- 한 영역에 하나만 사용

Secondary:

- 흰색 배경, Stroke 테두리, Text 색상
- 로그인, 취소, 다시 시도 같은 보조 행동

Tertiary:

- 투명 배경 또는 옅은 회색 배경
- 수정, 펼치기, 보조 이동

Danger:

- 삭제·초기화처럼 데이터나 세션에 영향을 주는 행동에만 사용
- 목록에서 항상 빨간 면으로 노출하지 않고 확인 단계에서 강조

공통:

- disabled, loading, hover, pressed, focus-visible 상태를 정의한다.
- 같은 역할의 버튼은 화면마다 색상과 높이를 바꾸지 않는다.
- 아이콘만 있는 버튼은 접근 가능한 이름을 제공한다.
- 행동 결과가 다른 버튼을 같은 시각 위계로 나열하지 않는다.

### 입력과 토글

- 입력에는 항상 라벨 또는 명확한 주변 문맥을 제공한다.
- focus에는 Primary 테두리와 ring을 함께 사용한다.
- 토글 라벨은 켜졌을 때 발생하는 결과를 설명한다.
- 저장이 필요한 선택과 즉시 반영되는 토글을 같은 방식으로 보이게 하지 않는다.

### 상태와 피드백

- 성공, 경고, 오류는 아이콘·색상·문구를 함께 사용한다.
- 화면에서 결과가 즉시 보이면 중복 토스트를 추가하지 않는다.
- 로딩 중에는 해당 컨트롤만 잠그고 관련 없는 화면 전체를 막지 않는다.
- 오류에는 가능한 다음 행동을 함께 안내한다.

## 모션

- 기본 전환은 150~220ms 범위로 제한한다.
- 접이식 영역, hover, 상태 변화에만 짧게 사용한다.
- 재생 상태를 제외한 장식용 반복 애니메이션은 사용하지 않는다.
- `prefers-reduced-motion`에서 핵심 동작을 잃지 않아야 한다.

## 접근성과 반응형

- 키보드로 모든 버튼, 입력, 탭과 details를 사용할 수 있어야 한다.
- focus-visible을 제거하지 않는다.
- 텍스트와 배경은 WCAG AA 수준 대비를 목표로 한다.
- 상태를 색상이나 이모지만으로 표현하지 않는다.
- 420px에서 행동 버튼이 겹치면 정보 아래로 자연스럽게 줄바꿈한다.
- 720px 이상에서 불필요하게 넓은 카드와 긴 텍스트 줄을 만들지 않는다.
- Electron 오른쪽 BrowserView와 겹치거나 가려지지 않는지 확인한다.

## 피해야 할 패턴

- 특정 서비스 화면의 픽셀 단위 복제
- 손님 화면의 블랙·형광·핑크 컬러 사용
- 플랫폼 색상을 큰 버튼이나 카드 배경으로 사용
- 모든 설정을 독립된 둥근 카드로 만드는 방식
- 같은 영역에 Primary 버튼 여러 개 배치
- 중요한 기능과 쿠키 초기화·개발자 도구를 같은 위계로 노출
- 설명, 도움말, 버튼에서 같은 내용을 반복
- 장식용 이모지, 그라데이션, glow, 과도한 그림자
- 화면 검증 없이 여러 컴포넌트의 인라인 스타일을 일괄 치환

## AI UI 변경 절차

1. 실제 컴포넌트, 상태 상수, Electron 연결 지점을 먼저 읽는다.
2. 한 컴포넌트의 사용자 목표와 주요 행동을 정한다.
3. 기존 동작을 유지하면서 시각 위계만 작은 단위로 변경한다.
4. 문구가 바뀌면 [WRITING_GUIDE.md](./WRITING_GUIDE.md)를 함께 확인한다.
5. 420px, 560px, 720px 폭과 실제 Electron 분할 화면에서 확인한다.
6. 키보드 focus, loading, disabled, error 상태를 확인한다.
7. `npm run build --prefix owner`를 실행한다.
8. 반복되는 새 결정이 생기면 이 문서를 갱신한다.

## UI 변경 체크리스트

- [ ] 영업 중 가장 자주 쓰는 행동이 먼저 보이는가
- [ ] 한 영역의 Primary 행동이 하나로 명확한가
- [ ] 상태와 행동이 시각적으로 구분되는가
- [ ] 예외·복구 기능이 기본 화면을 방해하지 않는가
- [ ] 플랫폼 색상을 작은 식별 요소에만 사용했는가
- [ ] 카드 중첩과 반복 설명을 줄였는가
- [ ] 같은 역할의 버튼, 입력, 상태가 일관적인가
- [ ] 420px에서도 버튼과 문구가 잘리지 않는가
