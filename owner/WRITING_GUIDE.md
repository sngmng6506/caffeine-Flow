# Owner Writing Guide

> **AI가 읽을 때:** `owner/src`의 버튼, 상태, 설정 설명, 빈 상태, 오류·성공 메시지를 추가하거나 바꿀 때
> **함께 갱신할 때:** 사장님 화면의 목소리, 핵심 용어 또는 반복되는 문구 패턴을 변경할 때
> **생략 가능한 경우:** 사용자에게 보이는 문구가 바뀌지 않는 로직·스타일 작업

Caffeine Flow 사장님 화면의 문구 기준이다. 시각 스타일과 컴포넌트 위계는 [DESIGN_GUIDE.md](./DESIGN_GUIDE.md)를 따른다.

## 목소리

문구는 **영업 중 옆에서 돕는 차분한 운영 파트너**처럼 말한다.

- 바로 이해되게: 현재 상태와 다음 행동을 먼저 알린다.
- 짧고 정확하게: 제목에서 말한 내용을 본문에서 반복하지 않는다.
- 부담 없이: 사용자의 잘못을 지적하지 않고 해결 방법을 안내한다.
- 과장 없이: 외부 음악 서비스와 AI의 결과를 보장하지 않는다.
- 운영 중심으로: 구현 방식보다 매장에서 일어나는 결과를 설명한다.

다른 서비스의 문구를 그대로 복사하지 않는다. 모든 문구는 Caffeine Flow의 실제 동작과 매장 운영 맥락에 맞게 쓴다.

## 기본 문체

- 화면·섹션 제목: 짧은 명사형
- 버튼: 행동 또는 결과가 드러나는 동사형
- 설명·오류·성공 메시지: 자연스러운 해요체
- 상태 배지: 짧은 현재형 또는 명사형
- 버튼, 탭, 배지에는 마침표를 쓰지 않는다.
- 문장에는 필요한 경우 마침표를 사용한다.
- 느낌표와 장식용 이모지를 사용하지 않는다.
- 말줄임표는 `...` 대신 `…`를 사용한다.
- 영문 서비스명은 공식 표기를 유지한다: `YouTube`, `YouTube Music`, `Spotify`, `SoundCloud`.

## 핵심 원칙

### 먼저 상태, 다음에 행동

문제가 있다는 사실만 말하지 않고 사용자가 다음에 할 수 있는 일을 안내한다.

- `재생 오류` → `곡을 재생하지 못했어요. 링크를 확인하고 다시 시도해 주세요.`
- `저장 실패` → `설정을 저장하지 못했어요. 잠시 후 다시 시도해 주세요.`
- `로그인 필요` → `Spotify 로그인이 필요해요. 로그인한 뒤 다시 재생해 주세요.`

### 버튼에는 실제 결과를 쓴다

`확인`, `계속`, `완료`처럼 결과가 모호한 표현을 단독으로 사용하지 않는다.

- 오른쪽 BrowserView에 서비스 페이지를 표시 → `오른쪽 화면에서 열기`
- 별도 인증 창 실행 → `로그인`
- 변경값 서버 반영 → `저장`
- 입력값 원래 상태로 복구 → `되돌리기`
- 신청곡 재생 확정 → `수락`

대상이 주변에서 명확하면 목적어와 `~하기`를 반복하지 않는다.

- 설정 편집 안의 버튼: `설정 저장하기`보다 `저장`
- 로그인 문제 해결 안의 버튼: `Spotify 로그인 정보 초기화`
- 위험 확인 창의 최종 버튼: `카페 삭제`처럼 대상을 명시

### 상태와 토글 문구를 구분한다

- 상태: `신청 받는 중`, `신청 닫힘`, `AI 필터 켜짐`
- 행동: `신청 닫기`, `AI 필터 끄기`

`ON`, `OFF`만 단독으로 쓰지 않는다. 공간이 좁아도 기능명과 상태를 함께 제공한다.
상태형 토글 버튼은 `신청 받는 중`, `AI 필터 켜짐`처럼 현재 상태를 표시하고, 접근 가능한 이름과 도움말에는 누르면 실행될 반대 행동을 제공한다.

### 기술 용어를 운영 결과로 바꾼다

- `BrowserView` → `오른쪽 화면`
- `recommendation` → `신청곡`
- `pending` → `새 신청`
- `accepted` → `대기 곡`
- `playing` → `재생 중`
- `slug` → `손님용 주소`
- `token 만료` → `로그인이 만료됐어요`
- `LLM error` → `AI 판단 중 문제가 발생했어요`

DevTools, API, UUID, Socket 같은 용어는 개발자 기능 외에는 노출하지 않는다.

### 한 문장에는 한 가지 핵심만 둔다

긴 설명 하나보다 상태와 해결 방법을 두 문장으로 나눈다.

```text
Spotify 로그인이 만료됐어요.
다시 로그인한 뒤 재생해 주세요.
```

## 핵심 용어

| 개념 | 사용자 용어 | 사용 기준 |
| --- | --- | --- |
| 손님이 추가한 음악 | 신청곡 | `추천곡`, `요청곡`과 혼용하지 않음 |
| 아직 결정하지 않은 신청 | 새 신청 | 내부 상태 `pending` |
| 재생하기로 정한 곡 | 대기 곡 | 내부 상태 `accepted` |
| 현재 나오는 신청곡 | 재생 중 | 내부 상태 `playing` |
| 처리된 기록 | 이력 | `히스토리`, `기록`과 혼용하지 않음 |
| 신청곡이 없을 때 나오는 음악 | 기본 BGM | `기본 영상`, `디폴트 음악`과 혼용하지 않음 |
| 손님 신청 접수 상태 | 신청 받는 중 / 신청 닫힘 | `영업 중`과 혼동하지 않음 |
| AI 심사와 통과 곡 자동수락 | AI 필터 | 켜짐 상태에서는 통과한 곡이 자동 수락됨을 설명 |
| AI 판단 기준 | 매장 분위기 설명 | `프롬프트`, `정책 문자열`을 노출하지 않음 |
| 손님이 접속하는 URL | 손님용 주소 | QR 문맥에서는 `QR 코드` 허용 |
| 외부 음악 페이지 영역 | 오른쪽 화면 | 일반 UI에서 `BrowserView` 금지 |
| 신청 가능한 외부 서비스 | 손님 신청 플랫폼 | 음악 서비스 바로가기와 구분 |
| BGM·로그인 진입점 | 음악 서비스 | `바로가기`보다 목적을 먼저 표현 |

새 용어가 여러 화면에 반복되면 이 표에 먼저 추가한다. 사용자 용어를 바꾸더라도 서버 상태값과 식별자는 임의로 바꾸지 않는다.

## 화면별 작성법

### 헤더

- 카페명은 장식 문구 없이 그대로 표시한다.
- 핵심 상태는 짧고 현재형으로 쓴다.
- 같은 상태를 색상, 배지, 설명에서 반복하지 않는다.

권장:

```text
신청 받는 중
AI 필터 켜짐
```

피함:

```text
현재 정상적으로 신청곡 접수가 진행 중입니다
AI AUTO ACCEPT ON
```

### 신청 목록

- 섹션 제목은 `기본 BGM`, `재생 중`, `대기 곡`, `새 신청`으로 통일한다.
- 내부 상태 변화보다 사장님이 이해할 결과를 쓴다.
- 곡 카드에서 대상이 명확하면 버튼은 `수락`, `건너뛰기`, `삭제`처럼 짧게 쓴다.
- 되돌릴 수 없는 행동은 확인 단계에서 대상을 다시 명시한다.

빈 상태:

```text
재생 중인 신청곡이 없어요.
대기 중인 곡이 없어요.
새로 들어온 신청곡이 없어요.
```

빈 상태에서 할 수 있는 행동이 있으면 한 문장을 덧붙인다. 행동이 없으면 억지로 안내를 추가하지 않는다.

### 기본 BGM

- 플랫폼 자체 자동재생과 다음 곡 동작을 Caffeine Flow가 보장하는 것처럼 쓰지 않는다.
- 단일 곡보다 재생목록이 안정적이라는 안내는 권장 표현으로 쓴다.

```text
기본 BGM에는 재생목록 사용을 권장해요.
```

`곡이 끝나면 자동으로 다시 재생됩니다`처럼 실제 구현에 없는 동작을 약속하지 않는다.

### 설정

- 대분류 제목은 기능의 목적을 쓴다: `운영 설정`, `매장 정보`, `음악 서비스`, `계정 및 도움말`.
- summary 설명은 한 문장으로 제한한다.
- 운영에 즉시 반영되는 설정은 `적용`, 계정·매장 정보를 기록하는 설정은 `저장`을 사용하고 완료 여부를 분명히 알린다.
- 변경이 없을 때 저장을 재촉하지 않는다.

```text
손님이 신청할 수 있는 음악 서비스를 선택하세요.
손님 신청 플랫폼을 적용했어요.
```

`허용 플랫폼`보다 `손님 신청 플랫폼`을 우선한다. 허용의 주체와 목적이 더 명확하기 때문이다.

### 음악 서비스

서비스별 계정 조건은 같은 문장 구조를 사용한다.

| 서비스 | 권장 안내 |
| --- | --- |
| YouTube | `로그인 없이 재생 가능` |
| YouTube Music | `무료 재생 가능 · 로그인 권장` |
| Spotify | `로그인 필요 · Premium 계정 필요` |
| SoundCloud | `로그인 없이 재생 가능` |

- `무료 재생 가능`은 유료 멤버십 없이 광고 포함 재생할 수 있다는 의미다.
- 국가, 콘텐츠, 외부 서비스 정책에 따라 로그인이 필요할 수 있으므로 결과를 절대적으로 보장하지 않는다.
- 서비스 열기 버튼은 `오른쪽 화면에서 열기`, 인증 창은 `로그인`으로 통일한다.
- 세션 초기화는 `로그인 문제 해결` 안에 두고 정상 사용 단계처럼 설명하지 않는다.

### AI 필터

- AI를 음악 추천기가 아니라 매장 분위기 기준의 자동 판단 기능으로 설명한다.
- `AI 필터`가 켜지면 통과한 곡이 자동으로 수락된다는 운영 결과를 함께 설명한다.
- AI의 정확도를 보장하거나 사람처럼 표현하지 않는다.
- 실패 시 자동 거절되는 현재 fail-closed 동작을 숨기지 않는다.
- 내부 모델명과 제공자는 테스트·진단에 필요한 경우에만 표시한다.

권장:

```text
매장 분위기 설명을 기준으로 신청곡을 확인해요.
AI 판단 중 문제가 발생하면 신청곡은 자동으로 거절돼요.
```

피함:

```text
AI가 완벽하게 매장에 어울리는 곡만 골라줘요.
```

### 로딩

- 무엇을 처리하는지 구체적으로 쓴다.
- 버튼 안에서는 짧게 쓴다.

```text
신청곡을 불러오고 있어요.
적용 중…
로그인 정보를 정리하고 있어요.
```

페이지 전체에 `로딩 중`만 단독으로 표시하지 않는다.

### 성공 메시지

- 완료된 결과를 짧은 과거형으로 알린다.
- 화면에서 결과가 즉시 보이면 성공 메시지를 중복으로 만들지 않는다.

```text
손님 신청 플랫폼을 적용했어요.
매장 정보를 저장했어요.
Spotify 로그인 정보를 정리했어요.
```

`정상적으로`, `성공적으로`는 대부분 생략한다.

### 오류 메시지

오류 문구는 다음 순서를 따른다.

1. 무엇을 완료하지 못했는지
2. 사용자가 지금 할 수 있는 행동

| 상황 | 권장 문구 |
| --- | --- |
| 설정 저장 실패 | `설정을 저장하지 못했어요. 잠시 후 다시 시도해 주세요.` |
| 신청곡 로드 실패 | `신청곡을 불러오지 못했어요. 다시 시도해 주세요.` |
| 외부 서비스 로그인 문제 | `{서비스명} 로그인을 완료하지 못했어요. 로그인 문제 해결을 확인해 주세요.` |
| 기본 BGM 재생 문제 | `기본 BGM을 재생하지 못했어요. 링크와 로그인 상태를 확인해 주세요.` |
| 인증 만료 | `로그인이 만료됐어요. 다시 로그인해 주세요.` |

- HTTP 상태, 오류 코드, API 원문을 일반 화면에 노출하지 않는다.
- 사용자 입력 문제여도 사용자를 탓하지 않는다.
- 실제로 제공하지 않는 복구 행동을 안내하지 않는다.

### 위험 행동과 확인

- 삭제, 주소 변경, 로그인 정보 초기화처럼 영향이 큰 행동은 결과를 먼저 설명한다.
- 취소 버튼과 위험 행동 버튼의 대상이 분명해야 한다.
- 위험 행동을 `확인`으로 축약하지 않는다.

```text
이 카페를 삭제할까요?
신청곡과 방문 기록이 함께 삭제되며 되돌릴 수 없어요.

[취소] [카페 삭제]
```

### 도움말과 문제 해결

- 정상 사용자는 읽지 않아도 되는 기술 설명을 기본 화면에 노출하지 않는다.
- 문제 해결 문구는 증상과 사용할 시점을 설명한다.

```text
Spotify 로그인이 반복해서 막힐 때만 사용하세요.
[Spotify 로그인 정보 초기화]
```

`DataDome`, `쿠키 마커` 같은 내부·외부 구현 용어는 개발자 도구 밖에서 사용하지 않는다.

## 피해야 할 표현

- `정상적으로`, `성공적으로`: 완료 사실만으로 충분하면 제거
- `해당`, `관련`, `진행`: 구체적인 대상을 직접 작성
- `유효하지 않은`, `요청 실패`: 사용자 관점의 문제로 바꿈
- `확인`, `계속`, `완료`: 결과가 모호한 버튼에 사용 금지
- `ON`, `OFF`: `켜짐`, `꺼짐` 또는 실제 상태로 표현
- `추천곡`, `요청곡`: 사장님 화면에서도 `신청곡`으로 통일
- pending, accepted, API, DB, Socket, slug, token 같은 구현 용어
- `무조건`, `완벽하게`, `곧`, `바로`: 보장할 수 없는 결과나 시간
- 반복되는 느낌표와 장식용 이모지
- 외부 서비스의 무료 재생, 자동재생, 계정 상태를 앱이 보장하는 표현
- 오류 해결과 무관한 긴 기술 설명

## AI 문구 변경 절차

1. 실제 컴포넌트와 연결된 동작을 먼저 확인한다.
2. 이 문서의 핵심 용어와 같은 개념의 기존 문구를 찾는다.
3. 버튼 문구가 실제 실행 위치와 결과를 정확히 설명하는지 확인한다.
4. 외부 서비스나 AI에 대해 보장하지 않는 내용을 약속하지 않는다.
5. 오류에는 가능한 복구 방법, 빈 상태에는 필요한 경우 다음 행동을 포함한다.
6. 여러 화면에 반복될 새 용어라면 구현 전에 이 문서를 갱신한다.
7. 문구 변경 후 `npm run build --prefix owner`를 실행한다.

## 문구 변경 체크리스트

- [ ] 문구만 보고 현재 상태와 다음 행동을 이해할 수 있는가
- [ ] `신청곡`, `기본 BGM`, `오른쪽 화면` 등 핵심 용어를 통일했는가
- [ ] 버튼 문구가 실제 실행 결과와 일치하는가
- [ ] 상태와 변경 행동을 혼동하지 않는가
- [ ] 제목과 설명이 같은 내용을 반복하지 않는가
- [ ] 오류가 가능한 해결 방법을 안내하는가
- [ ] 사용자를 탓하거나 불필요하게 불안하게 하지 않는가
- [ ] 내부 상태값과 개발 용어가 노출되지 않는가
- [ ] 외부 서비스와 AI의 결과를 과장하거나 보장하지 않는가
- [ ] 좁은 패널에서도 줄바꿈이 자연스러운 길이인가
