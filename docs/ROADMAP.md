## AI 음악 필터

### 수동 곡 라벨 기반 판단 입력

운영자가 확인한 곡 라벨을 충분히 모은 뒤, LLM 판단 전에 같은 플랫폼 원본 곡의 `operational` 라벨을 조회해 프롬프트 참고 데이터로 추가한다. 현재 곡의 라벨이 없을 때만 아티스트명을 정규화해 같은 아티스트의 다른 곡 라벨을 보조 참고로 조회한다.

```text
손님 신청 → 기본 플랫폼 메타데이터 확인
→ (platform, track_key)로 operational 라벨 조회
→ exact 라벨이 있으면 라벨 + 기본 메타데이터로 판단
→ 없으면 아티스트명을 정규화해 artist_key가 정확히 일치하는 참고곡 최대 3건 조회
→ 참고곡도 없으면 기본 메타데이터만으로 기존처럼 판단
```

정규화는 수동 라벨 저장에 쓰는 `normalizeArtistKey`를 재사용한다. NFKC 정규화, 소문자 변환, `- Topic`·`VEVO` 접미사 제거, 연속 공백 정리만 적용하고 유사 문자열 검색이나 자동 동일인 추정은 하지 않는다.

완료 조건:

- `evaluation` 라벨이 라이브 입력에서 제외됨
- exact 라벨은 플랫폼과 원본 곡 식별자가 정확히 일치할 때만 사용함
- 동일 아티스트 참고곡은 exact 라벨이 없을 때만, 정확히 일치하는 `artist_key`로, 최대 3건을 확정 정보가 아닌 참고 사례로 전달함
- 라벨이 없거나 조회에 실패하면 기본 메타데이터만으로 안전하게 판단함
- 사용한 라벨 ID·출처·스키마 버전을 감사 데이터로 추적함
- 기존 골드 라벨 비교에서 false accept가 악화되지 않음

### 자동 분위기 모델과 라이브 판단 확장

자동 분석값을 실시간 필터에 연결하는 것은 **2026-09-10에 구현했다**(운영자 판단, 골드 라벨 비교 전). 동작은 [LLM_FILTER.md](LLM_FILTER.md)에 있다. 남은 것은 그 연결이 실제로 나은지 재는 일이다.

남은 완료 조건:

- 사람 판정을 모아 자동 분석과 대조하고 false accept가 악화되지 않음을 확인함. 지금은 판정 표본이 거의 없다
- 분석이 붙은 곡과 붙지 않은 곡의 판단 품질을 나눠 비교함
- Valence/Arousal의 변별력을 다양한 장르에서 재확인함. 실측 21곡(전부 K-pop 계열)에서 valence·arousal 모두 70% 가까이가 중간 구간이었고 택소노미 무드는 76%가 `unknown`이었다. 표본이 치우친 것인지 모델 한계인지 아직 구분하지 못했다

### Audio LLM 무드 비교 테스트 — MAEST 검증 이후

Audio LLM 호출은 구현했고 기본으로 켜져 있다(`audio-analysis-worker/audio_llm.py`). 시스템 프롬프트는 Lab에서 고칠 수 있다. 모델별 비용은 1곡 기준으로 재봤고 기록은 [실험](../audio-analysis-worker/experiments/2026-09-10-audio-llm-model-cost.md)에 있다. 남은 것은 장르·길이가 다양한 곡으로 하는 비교다.

- 실제 신청곡 중 장르·길이·보컬 유무가 다양한 곡으로 오디오 입력 모델을 비교한다. 모델 ID·지원 형식·비용은 착수 시 확인한다.
- 곡 전체에서 3~5구간을 균등 샘플링한다. MAEST 결과나 고정 장르 택소노미를 프롬프트에 넣지 않는다.
- 자유 설명과 무드·악기·보컬·시간 변화 구조화 필드를 함께 받고 원문, 모델 ID, 프롬프트 버전, 샘플 구간, 입력 해시를 보존한다.
- 중간 융합 LLM은 두지 않는다. 최종 소비 시점의 판단에 두 원본을 활용하는 방식은 별도 평가한다.
- MAEST 단독 대비 사람의 검토·수정 부담, 무드 유용성, 지연·곡당 비용을 비교한 뒤 전체 호출 또는 선택 호출을 결정한다.
- 미실행 무드는 null을 유지한다. SELECTIVE 동작은 아직 선반영하지 않는다
- 3단 서술은 실시간 필터 프롬프트에 들어간다. 실측에서 제목만으로는 알 수 없는 근거(디스토션 기타 등)를 판단 사유가 인용했다. 다만 표본이 몇 곡이라 비교라고 부를 수 없다
- 소비 프롬프트의 MAEST 스타일 선택은 구현했다(`runs.selectPromptStyles`). 계수 0.5와 상한 5는 소수 표본의 잠정값이며 사람 검수 라벨이 쌓인 뒤 재검토한다

### MAEST 장르 캘리브레이션

Lab에서 확인·수정한 실제 신청곡을 검증 자료로 축적한다. 현재 taxonomy.json 임계값은 미보정 초기값이며, 검증 전 정확도로 표현하지 않는다. 장르별 표본을 확보한 뒤 태그별 PR-AUC·macro-F1과 임계값을 검토한다. 임계값 선정용 자료와 최종 평가 자료는 분리한다. 상세 장르 체계는 저장한 519개 원본 점수의 출현 분포를 보고 확장하며, 지역 태그만으로 약한 2순위 스타일을 강제로 채우지 않는다.

## 최신곡 수집

### SoundCloud 수집 소스

SoundCloud는 현재 수집 소스가 아니다. 붙이려면 **순위로 긁을 경로**가 먼저 필요하다.

검색(`scsearch`)은 동작하지만 쓰지 않는다. 수집의 목적이 카페에 어울리는 곡을 모으는 것이 아니라 필터가 판단할 곡을 모으는 것이라, 검색어로 장르를 좁히면 거절해야 할 곡이 표본에서 빠진다.

2026-09-11 실측에서 yt-dlp 2026.08.19로 차트 경로를 확인했고 전부 실패했다. `soundcloud:set` 추출기까지는 URL이 매칭되지만 그다음 API 호출이 404다.

| 시도한 URL | 결과 |
| --- | --- |
| `discover/sets/charts-top:all-music:kr` | 404 |
| `discover/sets/charts-top:all-music` | 404 |
| `discover/sets/charts-trending:all-music:kr` | 404 |
| `scsearch5:kpop 2026` | 정상 |

국가를 빼도 404라 한국 한정 문제가 아니다. yt-dlp의 차트 테스트 케이스는 `only_matching`이라 URL 매칭만 보장하고 실제 추출은 검증하지 않으므로, 테스트가 통과한다고 경로가 살아 있다는 뜻이 아니다.

남은 선택지:

- yt-dlp를 올려 차트 추출이 복구됐는지 확인한다. 다만 워커의 다운로드 경로 전체가 같은 버전을 쓰므로 수집만을 위해 올리지 않는다.
- `api-v2.soundcloud.com/charts`를 직접 부른다. 비공식 내부 API이고 `client_id`를 웹 페이지에서 긁어야 해 언제 막힐지 모른다.

어느 쪽도 지금 Apple·MusicBrainz 두 소스가 주는 표본을 넘어서는 값이 분명하지 않다. SoundCloud 음원은 손님이 신청한 링크로 이미 분석 큐에 들어오므로 다운로드 경로는 계속 검증된다.
