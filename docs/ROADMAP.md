# 로드맵

> **AI가 읽을 때:** 아직 구현되지 않은 기능을 검토하거나 설계 후보·우선순위를 논의할 때
> **함께 갱신할 때:** 새 개선 후보를 기록하거나 구현 완료·폐기로 후보 상태가 달라질 때
> **생략 가능한 경우:** 현재 구현의 버그 수정·리팩터링·동작 확인만 수행할 때

미구현 후보와 미완료 평가만 다룬다. 현재 동작은 [ARCHITECTURE.md](ARCHITECTURE.md), 신청 필터는 [LLM_FILTER.md](LLM_FILTER.md), 분석 실행은 [워커 README](../audio-analysis-worker/README.md)가 기준이다.

> 출시 약속이나 일정이 아니다. 실제 착수 항목은 GitHub Issue로 옮겨 범위와 완료 조건을 확정한다.

## AI 음악 필터

### Audio LLM 단독 심사 — 검토 중

곡이 들어온 뒤 사전 분석 DB 없이 오디오만으로 매장 적합성을 판단하는 후보다. **20–30초는 사용 가능성 검토 목표이며 달성한 성능이 아니다.** 현재 `main`의 비동기 다중 모델 분석·저장·신청 필터는 그대로다.

`audio-analysis-worker/benchmark_audio_llm.py`는 서술 지연 실험 도구이고, `server/scripts/filter-stability.js`는 같은 곡의 서로 다른 서술로 필터 판정이 갈리는지 재는 도구다. 둘 다 운영 큐와 DB에 쓰지 않으며 실행하면 외부 유료 API 요금이 발생한다. 한 번 받은 음원을 재사용하므로 다운로드+서술 합계는 추정치이며, 큐 대기·신청 처리·최종 심사·저장 시간은 제외한다. 이 수치를 서비스 응답시간으로 읽지 않는다.

판단에 필요한 평가:

- 다양한 길이·플랫폼·구간 설정으로 요청부터 최종 판단까지 지연과 실패율을 측정한다. 성공한 소수 호출의 분위수만으로 목표 달성을 선언하지 않는다.
- 매장 정책별 사람 판정과 대조해 오승인·오거절, 곡당 비용을 비교한다.
- 타임아웃·재시도·저장 범위는 결과를 보고 별도로 결정한다. 검증 전에 기존 fail-closed나 DB 보존 계약을 바꾸지 않는다.

### 수동 곡 라벨 기반 판단 입력

사람이 확인한 `operational` 라벨을 라이브 입력에 쓰는 후보다. 현재는 연결하지 않는다. 곡이 정확히 일치할 때 우선 사용하고, 없을 때만 `normalizeArtistKey`로 같은 아티스트의 참고곡을 제한적으로 조회한다. 아티스트 일치를 곡 특성의 정답으로 승격하지 않는다.

완료 조건:

- `evaluation` 라벨 제외, 플랫폼·원본 곡 식별자 exact 일치, 아티스트 참고 최대 3건
- 조회 실패·라벨 부재 시 기존 입력 유지, 사용한 라벨 ID·출처·스키마 버전 추적
- 매장별 골드 라벨 비교에서 false accept가 악화되지 않음. 다른 매장의 승인·거절은 복사하지 않음

### 자동 분위기 모델과 라이브 판단 확장

저장된 자동 분석의 라이브 입력 연결은 구현돼 있다. 남은 것은 품질 검증이다.

- 분석 포함·미포함 판단을 같은 골드 라벨로 비교하고 false accept를 확인한다.
- Valence/Arousal의 장르별 변별력과 MAEST 스타일 선택 규칙을 평가한다. 소수 표본의 결과·미보정 점수를 일반화하지 않는다.

### Audio LLM 비교 평가

호출·서술 저장·Lab 프롬프트 편집은 구현돼 있다. 과거 모델 비교는 [날짜별 실험 기록](../audio-analysis-worker/experiments/)이며 현재 가격·속도·품질의 보장이 아니다.

- 장르·길이·보컬 유무가 다양한 곡에서 모델·샘플 구간별 서술 품질, 검수 부담, 지연·비용을 비교한다.
- MAEST 태그 점수·임베딩·택소노미를 Audio LLM 입력에 넣지 않는다. Valence/Arousal은 예외다([가드레일](AI_CHANGE_GUARDRAILS.md#audio-analysis-contract)). 독립된 두 원본을 최종 판단에 활용하는 효과를 평가한다.
- 전체 호출과 선택 호출은 평가 후 결정한다. 미구현 `SELECTIVE` 모드를 현재 계약에 선반영하지 않는다.

### 1단에서 MAEST를 빼고 V/A만 남기기 — 적용함 (2026-09-17)

신청 시점 경로에서 MAEST를 빼고 `EMOTION_LLM` 모드를 쓴다. E2E가 약 90초에서 **24.9초**로 줄었다(1곡 실측).

근거가 된 측정:

- 운영 로그 90건 단계별 중앙값: **maest 76.6초**, emotion 7.7초, download 9.8초.
- MAEST는 자기 시간만 쓰는 것이 아니라 **같은 4코어를 나눠 쓰는 3단까지 4~5배 느리게** 만들었다. 3단 단독 16초가 MAEST와 동시에는 76초였고, 배율(4.4배·4.7배)이 두 측정에서 재현됐다.
- V/A는 결정론적이다(같은 파일에서 9월 9일 저장값과 소수점 16자리까지 일치). 3단이 듣는 구간에서만 구하면 6.0초가 1.0초가 되고 값 차이는 0.002였다.
- 44.1kHz 계열 특징(BPM·조성·danceability 등)은 신청 시점 판단에 쓰이지 않으면서 재디코딩까지 합쳐 곡당 5초를 썼다. 호환 CLI는 그대로 뽑는다.

**아직 재지 않은 것 — 이것이 남은 위험이다:**

- 필터가 `장르 후보`(MAEST)와 `템포`(BPM)를 잃었다. 그 공백이 판정을 바꾸는지 측정하지 않았다. `server/scripts/filter-stability.js`로 잴 수 있다.
- 남은 객관 신호는 V/A뿐인데, 과거 실측에서 **21곡(전부 K-pop) 중 valence·arousal 모두 70% 가까이가 중간 구간**이었다. 변별력이 약하면 판단이 사실상 3단 서술에만 실린다.
- 표본이 K-pop 1곡이다. 장르·길이·보컬 유무가 다른 곡으로 E2E와 실패율을 다시 봐야 한다.

### MAEST 장르 캘리브레이션

임계값·매핑은 `server/src/constants/music-taxonomy.json`이 기준이며 아직 미보정이다. 장르별 검증 표본을 확보해 PR-AUC·macro-F1과 임계값을 평가하고, 임계값 선정용 자료와 최종 평가 자료를 분리한다. 전체 서술에 대한 맞음·틀림만으로 개별 장르의 정답을 확정하지 않는다.

## 최신곡 수집

한국 한정 SoundCloud 인기 차트는 보류다. 2026-09-11 당시 확인한 차트 경로는 실패했지만, 이를 모든 SoundCloud 수집이 불가능하다는 뜻으로 확대하지 않는다. 현재 장르별 수집은 [워커 README](../audio-analysis-worker/README.md#최신곡-수집)를 따른다.

재검토 시 실제 응답·지역 범위를 확인한다. yt-dlp의 `only_matching` 테스트는 URL 매칭만 검증하므로 추출 성공의 근거로 쓰지 않는다.
