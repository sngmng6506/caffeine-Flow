# 문서 작성 원칙

> **AI가 읽을 때:** Markdown 문서를 추가·이동·분리하거나 문서 구조를 크게 바꿀 때
> **함께 갱신할 때:** 문서 체계, 단일 기준 위치, AI 문서 라우팅 규칙이 달라질 때
> **생략 가능한 경우:** 기존 담당 문서의 사실 한두 줄만 동기화할 때

## 기본 원칙

1. 한 사실은 한 문서에서만 자세히 설명하고, 다른 문서는 한 문장 요약과 링크만 둔다.
2. 현재 구현과 미래 계획을 분리한다.
3. 코드가 단일 기준인 세부 값(상수, 토큰, 허용값 목록)은 문서에 복사하지 않고 기준 파일을 가리킨다.
4. 문서는 독자와 질문 하나에 답하도록 유지한다. 담당 질문은 [README.md](README.md)에 있다.
5. AI 라우팅은 [AGENTS.md](../AGENTS.md)가 단일 기준이다. 충돌하면 `AGENTS.md`를 먼저 고친다.

## 문서 상단 메타정보

기준 문서는 제목 바로 아래에 세 줄을 둔다.

```markdown
> **AI가 읽을 때:** 이 문서를 읽어야 하는 구체적인 변경 조건
> **함께 갱신할 때:** 코드 변경과 함께 이 문서를 수정해야 하는 조건
> **생략 가능한 경우:** 이 문서를 읽지 않아도 되는 대표적인 작업
```

- 추상적인 표현 대신 파일·기능·계약을 구체적으로 적는다.
- 모든 작업에서 읽으라고 하지 않는다.
- 내부 리팩터링과 외부 동작 변경을 구분한다.
- 메타정보에 기능 설명을 반복하지 않는다.

## 갱신 판단

- 외부 동작이나 유지해야 할 계약이 바뀌면 담당 문서를 갱신한다.
- 파일 분리·함수 추출처럼 동작이 같은 리팩터링은 문서를 바꾸지 않는다.
- 구현되지 않은 제안은 [ROADMAP.md](ROADMAP.md)에 둔다.
- 코드와 문서가 다르면 코드·상수·테스트·DB 제약을 함께 확인하고 불일치 원인을 먼저 판단한다.

## 피해야 할 패턴

- API 문서에 긴 설계 배경 작성
- 기능 문서마다 환경변수 목록이나 같은 상태표 반복
- 가드레일에 기능 설명 복사
- 구현되지 않은 API나 테이블을 현재 동작 문서에 기재
- 모든 작업에서 모든 문서를 읽도록 지시
- 코드 변경과 대규모 문서 재구성을 한 커밋에 처리
