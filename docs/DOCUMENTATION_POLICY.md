# 문서 작성 원칙

> **AI가 읽을 때:** Markdown 문서를 추가·이동·분리하거나 문서 구조를 크게 바꿀 때
> **함께 갱신할 때:** 문서 체계, 단일 기준 위치, AI 문서 라우팅 규칙이 달라질 때
> **생략 가능한 경우:** 기존 담당 문서의 사실 한두 줄만 동기화할 때

## 기본 원칙

1. 한 사실은 한 문서에서만 자세히 설명한다.
2. 다른 문서에서는 한 문장 요약과 링크만 제공한다.
3. 현재 구현과 미래 계획을 분리한다.
4. 코드가 단일 기준인 세부 값은 문서에 과도하게 복사하지 않는다.
5. 문서는 독자와 질문 하나에 답하도록 유지한다.
6. AI는 모든 문서를 읽지 않고 `AGENTS.md`의 작업별 라우팅을 따른다.

## 문서 상단 메타정보

기준 문서는 제목 바로 아래에 다음 세 줄을 둔다.

```markdown
> **AI가 읽을 때:** 이 문서를 읽어야 하는 구체적인 변경 조건
> **함께 갱신할 때:** 코드 변경과 함께 이 문서를 수정해야 하는 조건
> **생략 가능한 경우:** 이 문서를 읽지 않아도 되는 대표적인 작업
```

작성 원칙:

- 추상적인 표현보다 파일·기능·계약을 구체적으로 적는다.
- 모든 작업에서 읽으라고 하지 않는다.
- 내부 리팩터링과 외부 동작 변경을 구분한다.
- 메타정보에 기능 설명을 반복하지 않는다.
- 중앙 라우팅과 충돌하면 `AGENTS.md`를 먼저 고친다.

## 문서 선택

- 제품 소개: `README.md`
- 시스템 구조: `ARCHITECTURE.md`
- Electron 재생: `PLAYBACK.md`
- API 경로: `API.md`
- 개발·배포: `DEVELOPMENT.md`
- AI 음악 필터: `LLM_FILTER.md`
- 변경 금지 계약: `AI_CHANGE_GUARDRAILS.md`
- 미구현 계획: `ROADMAP.md`

작업별 필수 읽기 조합은 루트 `AGENTS.md`를 기준으로 한다.

## 문서 갱신 판단

- 외부 동작이나 유지해야 할 계약이 바뀌면 담당 문서를 갱신한다.
- 파일 분리·함수 추출처럼 동작이 같은 내부 리팩터링은 문서를 억지로 바꾸지 않는다.
- 구현되지 않은 제안은 현재 동작 문서가 아니라 `ROADMAP.md`에 둔다.
- 코드와 문서가 다르면 코드·상수·테스트·DB 제약을 함께 확인하고 불일치 원인을 먼저 판단한다.

## 피해야 할 패턴

- API 문서에 긴 설계 배경 작성
- 기능 문서마다 환경변수 목록 반복
- 가드레일에 기능 설명 복사
- 구현되지 않은 API나 테이블을 현재 문서에 기재
- 같은 상태표를 여러 문서에 중복 작성
- 모든 작업에서 모든 문서를 읽도록 지시
- 커밋에서 코드 변경과 대규모 문서 재구성을 함께 처리

## 문서 변경 체크

- [ ] 이 정보의 단일 기준 문서가 어디인지 정했다.
- [ ] `AGENTS.md`의 라우팅과 충돌하지 않는다.
- [ ] 읽기·갱신·생략 조건이 구체적이다.
- [ ] 기존 문서의 중복 설명을 제거했다.
- [ ] 현재 구현인지 계획인지 명확하다.
- [ ] 링크와 제목 anchor가 유효하다.
- [ ] API·가드레일 CI가 확인하는 문자열을 유지했다.
