# 역할이 다른 두 구간으로 바꾼다 (2026-09-19)

구간을 고르는 방식을 균등 배치 → 에너지 기반 → **슬롯 구성**으로 두 번 바꾼 과정과, 그 끝에 MAEST를 완전히 걷어낸 기록이다.

## 측정 조건

- 곡 3개. 카테고리마다 하나씩, 전략마다 8회
  - 재즈→빅밴드 [Q4_qJi_jrUg](https://www.youtube.com/watch?v=Q4_qJi_jrUg) (186초)
  - K-pop [lhdR628kqUM](https://www.youtube.com/watch?v=lhdR628kqUM) (176초)
  - trap/lo-fi [yCcvpI-8E4I](https://www.youtube.com/watch?v=yCcvpI-8E4I) (176초)
- 입력: 2구간 × 15초, 24kbps mp3. 구간마다 고른 근거를 프롬프트에 적는다
- 모델 `google/gemini-2.5-pro`, 프롬프트 `audio-llm-3`, 필터 `anthropic/claude-sonnet-5`
- 매장 정책 — "실제 악기 연주가 살아있는 곡 선호, 신디사이저·전자음 위주는 회피"
- **곡 3개, 카테고리당 1곡.** 파라미터를 확정하기엔 부족하다.

`mood`는 카테고리를 갈랐다 — 재즈 `경쾌한(7)·신나는(6)`, K-pop `활기찬(4)·감성적인(3)`, trap `차분한(5)·몽환적(4)`. 세 곡 V/A가 모두 `중간 · 중간`이었던 것과 대조적이다.

## 읽어낼 것

**1. 한 벌의 구간으로 두 문제를 풀고 있었다.**

분위기(V/A·mood)는 곡 평균을 추정하는 문제이고, 정책 위반 탐지는 이상치를 찾는 문제다. 최적해가 다른데 같은 구간을 썼다.

전곡 V/A를 정답으로 보고 각 방식의 오차(valence+arousal 절대오차 합)를 재면:

| 곡 | 균등 3x15 | 에너지 3x15 | 후렴 구간 |
| --- | ---: | ---: | ---: |
| 재즈 | 0.044 | 0.104 | 0.091 |
| K-pop | 0.022 | 0.031 | **0.017** |
| trap | 0.124 | 0.088 | **0.068** |
| **최악값** | 0.124 | 0.104 | **0.091** |

에너지 기반은 재즈 valence를 0.609 → 0.681로 올려 **밴드 경계(0.65)를 넘겼다.** 곡은 그대로인데 `중간`이 `밝음`이 된다. 균등은 반대로 인트로·아웃트로를 물어 활력을 과소평가한다(trap arousal 0.443 → 0.346).

**2. 고정 중앙 30초는 쓸 수 없다. ±15초 여유가 고친다.**

| 곡 | 고정 중앙 | ±15초 | ±30초 |
| --- | ---: | ---: | ---: |
| 재즈 | 0.51 | 0.95 | 0.97 |
| K-pop | 0.90 | 0.91 | 1.00 |
| trap | **0.37** | **1.00** | 1.00 |

고정 중앙은 세 곡 중 둘이 탐색 경계에 붙고 에너지가 0.37~0.51이다. ±15초를 주면 0.91 이상으로 올라간다. ±30초부터는 "중앙"의 뜻이 사라져 에너지 기반 선택과 같아지므로 ±15초로 정했다.

**3. 후렴 탐지와 하이라이트는 같은 알고리즘이다.**

처음 안은 `RefraiD 하이라이트 + 중앙 30초 + 훅 구간` 세 슬롯이었다. K-pop에서 1번과 3번이 **3초 차이로 붙었다**(155초 vs 158초) — 후렴 구조가 제대로 있는 곡에서 그랬다는 것이 핵심이다. 방법이 잘 작동할수록 두 슬롯이 같은 답을 낸다.

**4. RefraiD 구현을 직접 옮겼고, 축약본은 못 쓸 수준이었다.**

직접 쓴 축약본(지배적 지연 하나만 추적)은 trap 후렴을 `0~40초`(도입부, 에너지 0.11)로 잡았다. pychorus는 같은 곡에서 `137초`(에너지 0.88)를 찾았다. 차이는 **선분 검출과 겹침 집계**였다 — 축약본이 뺀 부분이다.

pychorus를 numpy로 옮긴 결과(`chorus.py`, 곡당 0.32~0.47초):

| 곡 | 포팅본 | pychorus | `min_length` 10/12/15/20 안정성 |
| --- | --- | --- | --- |
| trap | 139~158초 | 137초 | 141 / 141 / 139 / 138 |
| K-pop | 72~132초 | 88초 | 121 / 72 / 72 / 72 |
| 재즈 | 94~118초 | 79초 | 94 / 94 / 94 / 94 |

포팅본이 **파라미터에 더 안정적이다.** pychorus는 `clip_length` 10↔15에서 K-pop 후렴을 60초→88초로 옮기는데 포팅본은 12 이상에서 고정이다.

**차이의 원인은 로직이 아니라 크로마다.** 같은 크로마를 양쪽에 넣어 단계별로 대조했다.

| 단계 | 결과 |
| --- | --- |
| 선분 검출 | 동일 |
| 선분별 겹침 점수 | 동일 |
| 최종 선택 | 동일 (`start 426, end 637, lag 318`) |
| 시간-지연 행렬 | 최대차 0.80 — 아래 참조 |

librosa 크로마를 포팅 로직에 넣으면 세 곡 모두 pychorus와 시작점이 소수점까지 일치한다(재즈 79.1, K-pop 87.8, trap 137.2). 남는 차이는 전부 **librosa `chroma_stft`의 필터뱅크 분배 vs 포팅본의 FFT 빈 하드 할당**에서 온다.

**pychorus의 빠른 구현은 자기 참조 구현과 다르다.** `compute_similarity_matrix`가 `np.tile`로 순환 반복을 만들어, `지연 > 시간`인 영역(비교할 과거가 없는 자리)에 곡 끝과 앞을 비교한 값이 들어간다. 같은 파일의 `compute_similarity_matrix_slow`는 그 자리를 0으로 둔다. 포팅본은 참조 구현을 따랐다.

순환 반복본으로 바꿔 세 곡을 다시 돌려도 **결과가 같았다** — `denoise` 끝의 `np.triu`와 선분 검출(`col >= row`)이 그 영역을 다시 잘라내기 때문이다. 의미상으로도 비교할 과거가 없는 자리는 0이 맞다.

**5. 크로마는 악기 변화를 보지 못한다.**

RefraiD는 음색을 버리고 화성만 남기는 표현을 쓴다. 편곡이 달라도 같은 후렴으로 인식하는 강점의 근원이지만, **매장 정책이 가리키는 바로 그 변화에 눈을 감는다.** 코드 진행이 같고 리드만 브라스에서 신스로 바뀐 구간은 RefraiD에게 같은 구간이다.

재즈 곡 `150~182초`를 못 찾은 것은 구현 문제가 아니라 방법의 성질이다. MFCC 노벨티도 같은 지점에 반응하지 않았다(국소 최대 세기 3.9, 곡선 중앙값 2.4).

**6. 전조 대응은 이 곡들에서 쓸모가 없었다.**

RefraiD의 상징인 12방향 크로마 이동을 재 봤다. 세 곡 모두 무전조가 1위이거나(K-pop 0.7773, trap 0.7895) 차이가 잡음 범위였다(재즈 +6반음 0.8499 vs 무전조 0.8442, 0.7% 차). 상위권에 올라오는 +5·+7반음은 완전4도·5도라 조성 음악이면 어디서나 나오는 부산물이다.

## MAEST를 걷어낸 이유

신청 시점 경로에서는 2026-09-17에 이미 뺐다. 곡당 76초를 쓰면서 같은 4코어를 나눠 쓰는 3단까지 4~5배 느리게 만들었다(실측: 3단 단독 16초, 동시 76초). E2E 약 90초 → 25초.

이번에 **읽는 경로까지 지웠다.** 남겨 둔 이유는 "저장된 행을 읽기 위해서"였지만, 그 사이 소비처가 사실상 사라졌다:

- 필터 프롬프트의 장르 후보 — 신규 분석에는 없고 옛 행에만 있어, 곡마다 있고 없고가 갈렸다
- Lab의 상위 스타일 표 — 운영자가 보지 않기로 했다
- `renormalize` — 다시 접을 택소노미가 없다

데이터는 지우지 않았다. `music_audio_runs.payload`의 옛 `maest_raw`는 그대로 있고 append-only 트리거가 지킨다. 컬럼도 `maest_summary` → `analysis_summary`로 이름만 바꿨다. 되살리려면 모델·검증·저장·소비처를 한 작업에서 함께 되살려야 한다.

## 결론에 못 쓴 것

- **정답을 모른다.** 재즈 `150~182초`의 리드가 신스인지 오르간·기타인지 사람이 듣고 확인하지 않았다. 2슬롯이 그 구간을 안 듣는 것이 개선인지 후퇴인지 판정할 기준이 없다.
- **이 구성은 후렴 밖 특이 구간을 구조적으로 못 듣는다.** 세 슬롯 모두 대표성을 재는 자리이고, 크로마는 음색을 버리며 중앙 슬롯은 위치가 고정이다. 매장 정책이 악기를 가리키는데 그 악기가 후렴 밖에만 나오면 놓친다. 운영자가 트레이드오프를 알고 택했다.
- **구성 설명 문구의 효과를 확인하지 못했다.** 라벨만 준 조건과 구성 설명을 더한 조건에서 전자음 언급 1/8 vs 2/8, 기타 언급 4/8 vs 2/8로 n=8 잡음 범위였다. 유지한 것은 "고르게 뽑았다"가 거짓이기 때문이지 측정된 이득 때문이 아니다.
- **카테고리당 1곡이다.** K-pop·trap의 전원 거절은 정책상 맞는 동작으로 보이지만, 곡이 하나씩이라 필터가 그 카테고리를 제대로 가르는지는 모른다.
- **포팅본과 pychorus가 재즈에서 갈린다.** 이 문서 앞부분의 카테고리 측정은 pychorus 구간으로 잰 것이고, 운영에 들어간 것은 포팅본이다. 재즈는 79초 ↔ 94초로 다른 구간을 듣는다. 원인은 크로마 계산이며 로직은 대조로 같음을 확인했지만, **어느 크로마가 더 나은지는 재지 않았다.** 필터뱅크를 옮기면 맞출 수 있고 100줄 남짓이다.
- **긴 곡을 검증하지 못했다.** 유사도 행렬이 프레임 수의 제곱이라 10분 곡에서 peak RSS 1335MB가 나와 프레임 수를 1200으로 묶었다(0.6초/455MB). 307초를 넘는 곡은 시간 해상도가 0.256초에서 최대 0.5초로 떨어지는데, 표본이 전부 3분대라 그 구간의 곡으로 확인하지 못했다.
- **P90 26초는 목표(20~30초) 안이지만 여유가 4초다.** 3단 API에서 55초·75초 이상치를 관측한 적이 있고 폴백 정책은 여전히 없다.

## 재현

```bash
cd audio-analysis-worker
python benchmark_audio_llm.py --platform youtube --track-key '<VIDEO_ID>' \
  --strategies 2x15 --repeats 8 --with-va --va-style number \
  --output ~/bench.json

cd .. && node server/scripts/filter-stability.js --benchmark ~/bench.json \
  --title '<제목>' --artist '<아티스트>' --policy '<매장 정책>' \
  --repeats 3 --output ~/verdict.json
```

구간을 밖에서 정해 넣으려면 `--segments-json`에 `{selection, segments}`를 준다. 두 도구 모두 운영 큐·DB에 쓰지 않는다. 실행하면 외부 유료 API 요금이 발생한다.
